# Review Findings — 1.1.0 (2026-08-04)

Comprehensive review of claims, implementation, tests, and documentation
against LocalWebAuthn 1.1.0. Continues from [REVIEW-20260730.md](REVIEW-20260730.md).

Status key: ✅ fixed ◷ deferred ✘ not started

## Must Fix

### ✅ 1. `cleanup()` deletes valid passkeys

**Severity: critical correctness / availability**

#### Finding

`cleanup()` deletes expired _and revoked_ sessions, then deletes any credential
that has no remaining session rows and is older than one hour
(`SQL.deleteOrphanedCredentials` + `ORPHANED_CREDENTIAL_GRACE_MS`).

A credential with no open session is the **normal idle state** of every
passkey — after logout, absolute session expiry, or cleanup of revoked sessions.
It is not evidence of a failed D1 batch.

SECURITY.md claims orphaned credentials “cannot be used to authenticate without
a session row.” That is false: authentication is
`getCredential` → verify signature → `completeAuthentication` (which creates a
new session). No pre-existing session is required.

#### Reproduction (any official store)

```ts
// After a successful enrollment + registration that yields sessionToken:
await auth.revokeSession(sessionToken); // logout
// advance the injectable clock (or wall clock) by > 1 hour
await auth.cleanup();
expect(await auth.listCredentials(userId)).toHaveLength(0); // BUG: should remain 1
```

Same failure after waiting past `sessionAbsoluteMs` without logout, then
`cleanup()`.

#### Plan

1. Remove `deleteOrphanedCredentials` and `ORPHANED_CREDENTIAL_GRACE_MS` entirely
   — do not replace them with a “safer” credential sweep.
2. Drop `CleanupResult.orphanedCredentials`; cleanup has no credential dimension.
3. Correct SECURITY.md, MIGRATING.md, package README, and TSDoc: cleanup is only
   grants/challenges/sessions; credentials are managed by registration/revocation.
4. Tests: logout → cleanup → credential remains and authentication works.

**Done**: No credential cleanup path remains. `orphanedCredentials` is removed
from `CleanupResult`. Conformance and service tests prove cleanup leaves
credentials intact.

### ✅ 2. SECURITY / ops docs recommend unsafe cleanup

#### Finding

SECURITY.md and `@localwebauthn/server` README tell operators to schedule
`cleanup()` every few minutes. Following that guidance with 1.0.0–1.1.0 will
eventually wipe passkeys for any user who is not continuously logged in.

#### Plan

Ship the code fix in item 1, then rewrite cleanup guidance: reaps expired
grants, consumed/expired challenges, and dead sessions only; never credentials.
Add an explicit “credentials are durable” sentence next to the scheduling note.

**Done**: SECURITY.md, server package README, types TSDoc, and MIGRATING.md
describe durable credentials and safe cleanup scheduling.

## Should Fix

### ✅ 3. Audit trail gaps on the highest-risk operations

#### Finding

- `revokeSession` emits `session.revoked` without `userId` / `credentialId`.
- `revokeUserAuthentication` (the recovery bulk-revoke) emits **no events**.

Recovery documentation stresses auditability; the API does not deliver it.

#### Plan

1. Change store `revokeSession` to `UPDATE … RETURNING user_id, credential_id`
   and return `{ userId, credentialId } | null` (breaking for custom stores —
   document in MIGRATING).
2. Service keeps public `revokeSession(token): Promise<boolean>` but populates
   the event identity from the store result.
3. Emit `user.authentication_revoked` from `revokeUserAuthentication` with
   `userId` after the store call succeeds.
4. Tests: event payload after logout; event after `revokeUserAuthentication`.

**Done**: Store `revokeSession` uses `RETURNING` and returns identity.
`session.revoked` includes `userId`/`credentialId`. New event
`user.authentication_revoked`. Covered by service tests.

### ✅ 4. SQLite foreign keys not enforced by the adapter

#### Finding

The schema uses `REFERENCES`, but SQLite only enforces FKs when
`PRAGMA foreign_keys = ON`. Tests and the demo set it; `migrateSqlite` and
`SqliteLocalWebAuthnStore` do not. Hosts that open a connection without the
pragma get silent non-enforcement.

#### Plan

1. Enable `PRAGMA foreign_keys = ON` in `migrateSqlite` and in the store
   constructor (per-connection; same `Database` handle is the common case).
2. Document in the SQLite package README / SECURITY storage section that each
   SQLite connection must keep foreign keys on (the adapter does this for the
   connection it is given).

**Done**: `PRAGMA foreign_keys = ON` in `migrateSqlite` and the store
constructor; documented in SECURITY.md and the package README.

### ✅ 5. Counter compare-and-swap allows regression

#### Finding

`advanceCredentialCounter` only requires `counter = previousCounter`. It does
not enforce WebAuthn’s “must strictly increase when either value is non-zero”
rule. Default SimpleWebAuthn rejects regressions; a custom `CeremonyProvider`
could still write a lower counter.

TSDoc that says the store “rejects counter values that do not advance” is
overstated (0→0 is valid; non-zero non-increase is not enforced at the store).

#### Plan

1. In the service, before `completeAuthentication`, reject when
   `(previous > 0 || next > 0) && next <= previous` with `authentication_failed`.
2. Mirror the rule in SQL: `AND (? > counter OR (counter = 0 AND ? = 0))` with
   `newCounter` bound twice.
3. Conformance / service test with a ceremony mock that returns a non-increasing
   non-zero counter.

**Done**: Service pre-check plus SQL predicate on `advanceCredentialCounter`.
Store and service tests cover non-increasing non-zero counters.

### ✅ 6. `last_credential` check is TOCTOU

#### Finding

The service lists active credentials, then calls `revokeCredential`. Two
concurrent revokes can each observe “more than one active” and remove both.

#### Plan

1. Move last-credential protection into the store revoke path with a single
   conditional `UPDATE` (or transaction) so the check and revoke commit together
   on SQLite/PostgreSQL.
2. Extend `revokeCredential` store signature to accept
   `{ allowLastCredential?: boolean }` and return a result that distinguishes
   `revoked` / `not_found` / `last_credential` (or keep boolean + throw at
   service after a dedicated store result type — prefer a small result union).
3. D1: same SQL condition in the revoke statement (single-statement check is
   enough for the last-credential predicate; session revoke remains best-effort
   batch as today).
4. Service maps `last_credential` → `LocalWebAuthnError` as today.
5. Test concurrent dual-revoke leaves at least one credential when
   `allowLastCredential` is false (SQLite/Postgres).

**Done**: Conditional `UPDATE` with `EXISTS` other active credential; store
returns `'revoked' | 'not_found' | 'last_credential'`. Service maps
`last_credential` to the existing error. Conformance covers refuse / allowLast.

### ✅ 7. No service-level test for session-authorized second passkey

#### Finding

Adding a passkey while authenticated is a primary product path. Unit tests only
exercise enrollment-grant registration; the second-passkey path appears only in
Playwright e2e.

#### Plan

Add a service test: enroll + register credential A → `registrationOptions` /
`verifyRegistration` with `sessionToken` → listCredentials length 2; emit
`credential.registered` without a second `enrollment.completed`.

**Done**: Service test registers a second credential via `sessionToken` and
asserts no extra `enrollment.completed`.

### ✅ 8. Demo last-credential error uses message strings

#### Finding

`examples/demo/src/application.ts` detects the last-passkey case via
`error.message.includes('final active credential')` instead of
`isLocalWebAuthnError` / `code === 'last_credential'`.

#### Plan

Use `isLocalWebAuthnError(error) && error.code === 'last_credential'`.

**Done**: Demo passkey revoke handler uses `isLocalWebAuthnError` and
`error.code === 'last_credential'`.

## Implementation Notes

### Breaking store-contract changes (documented in MIGRATING)

- `revokeSession` returns `{ userId, credentialId } | null` instead of `boolean`.
- `revokeCredential` accepts optional `allowLastCredential` and returns
  `'revoked' | 'not_found' | 'last_credential'` instead of `boolean`.
- `CleanupResult.orphanedCredentials` removed; no credential cleanup.

### Released as 1.2.0

All Must Fix and Should Fix items are closed. Remaining nice-to-haves are
deferred (WAL stress tests, D1 failure injection, host cookie/origin helpers).

## Summary

1.1.0 had a critical cleanup bug that could destroy idle credentials, plus
audit/FK/counter/last-credential gaps. 1.2.0 removes credential cleanup
entirely (no safer sweep — credentials are not cleaned up at all), tightens
store contracts for audit and atomic last-credential protection, enforces
counter monotonicity, enables SQLite foreign keys, and adds regression coverage
for the paths that would have caught the cleanup bug.
