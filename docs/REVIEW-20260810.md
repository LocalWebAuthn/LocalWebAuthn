# Post-v3.0.0 correctness review (2026-08-10)

Reviews the changes merged after `v3.0.0` through `main` at
`96fdf3189fc5bc8fa534a8fcbe70b2b081bbe4ac`. The request called the branch `master`, but
this repository has no local or remote `master` ref: `main` tracks `origin/main`, and
`origin/HEAD` points to it.

This began as an open remediation handoff. All five findings were addressed on
`fix/telemetry-state-fidelity` on 2026-08-12. The resolutions below preserve credential
state-machine semantics: callbacks observe committed results, callback failures are
contained, and durable delivery remains the host's responsibility through an outbox if
best-effort in-process observation is insufficient.

## Reviewed change set

`v3.0.0..main` contains five non-merge commits:

1. `a46a81d` — Tell a D1 guard trip apart from a broken database
2. `4f2ae15` — Say why an enrollment link was refused
3. `addbbcd` — Tell every channel when a passkey is created
4. `6154744` — Make revocation explicit, and schedule the reaping nothing scheduled
5. `649b252` — Report the signup lifecycle, so reaping does not erase the record

The review followed the changes through the server and browser packages, all three
official stores, the channel helpers, the demo host, generated package artifacts,
documentation, and tests. It paid particular attention to whether new observational
features remain observational, whether the audit stream describes transitions that
actually committed, and whether cleanup and notification claims match the paths that
produce them.

## Executive verdict

The D1 guard change, official-store enrollment diagnosis, and explicit kind check in the
demo's claim handler are internally consistent and well tested. No new authorization
bypass was found in the server package.

The review found five concerns, all now addressed:

1. A configured signup event sink can turn an observational hook into a failed request
   after state has already changed, and an asynchronous sink is silently not awaited.
2. `signup.canceled` is emitted for conditional-update no-ops, while recovery
   cancellations caused by passkey sign-in are not emitted at all.
3. The passkey-created notice says an enrollment link and a channel were compromised for
   every registration, including credentials added through an authenticated session.
4. The documented compatibility behavior for a custom store without
   `enrollmentGrantState` disagrees with the error the service actually returns.
5. Cleanup deletes grants before challenges, so an expired grant referenced by a
   finished challenge always needs a second cleanup sweep.

Items 1 to 3 were corrected before presenting the audit and notification paths as
production patterns. Items 4 and 5 were closed in the same correctness pass.

## 1. Signup event sinks can fail requests after state has changed

**Severity: medium — correctness, availability, and audit reliability**

**Status: fixed on `fix/telemetry-state-fidelity`**

### Resolution

- `SignupEventSink` now permits any return value for source compatibility, while
  `bestEffortSignupEventSink` awaits returned promises, preserves event order, and
  contains both sink failures and failures from the optional error reporter.
- `createDemoApplication` constructs one protected sink and shares it with signup routes,
  credential-authentication cancellation reporting, and the scheduled reaper. Every route
  awaits it after the corresponding write, so synchronous throws and asynchronous
  rejections are logged but cannot alter the HTTP or credential-state outcome.
- A successfully judged `proved` outcome is persisted before its proof event is delivered.
- `reapSignups` deletes with `RETURNING`, then emits one event for each row actually
  deleted. A failed sink therefore cannot retain expired personal data or make the sweep
  appear rolled back.

This is explicitly best-effort. A deployment that requires lossless audit delivery must
write an outbox record in the same transaction as the state transition; no callback
invoked after commit can provide that guarantee.

### Finding

`examples/channels/src/signup.ts` defines:

```ts
/** Where a host sends SignupEvents. Never throws into the caller. */
export type SignupEventSink = (event: SignupEvent) => void;
```

The demo accepts one as `DemoApplicationOptions.onSignupEvent`, but passes it directly to
`mountSignupRoutes`. Every route calls `emit(...)` without a safety boundary. This differs
from `LocalWebAuthn.#emit`, which catches event-handler failures and logs them because the
authentication write may already have committed.

The first call in `/api/signup/start` demonstrates the problem clearly:

1. `insertSignup` commits a `demo_signups` row.
2. The route calls `emit({ type: 'signup.started', ... })`.
3. Only after the callback returns does the route construct and return the simulated proof
   messages.

If the sink throws, Hono's error handler returns 500. The row exists, but the caller never
receives the proof links needed to continue it. Similar partial outcomes occur after
`markSignupProved`, `markSignupPending`, client creation, enrollment issuance, claim
counting, and cancellation.

There is a second API-shape problem. TypeScript permits an `async` function where a
void-returning callback is expected. The route neither detects nor awaits the returned
promise, so an asynchronous audit write can still be in flight after the response and a
rejection can become an unhandled rejection.

`reapSignups` has the same direct callback behavior. It emits `signup.reaped` before the
delete, deliberately. A throwing sink aborts the function before any rows are deleted;
the server catches the sweep failure and retries later. That may be the desired
fail-closed policy for a _durable_ audit sink, but an in-process callback is not durable,
and the public `SignupEventSink` contract currently promises that it will not throw into
the caller. The route and cleanup semantics need one explicit policy rather than an
accidental mixture.

### Deterministic reproduction

Add a temporary test beside the existing lifecycle tests in
`examples/demo/tests/application.test.ts`. Reuse its `setup` and `startSignup` helpers:

```ts
it('shows that a throwing signup sink fails start after persistence', async () => {
  const { app, database } = setup({
    onSignupEvent: () => {
      throw new Error('audit sink unavailable');
    },
  });

  const response = await app.request('/api/signup/start', {
    method: 'POST',
    headers: { Origin: publicOrigin, 'Content-Type': 'application/json' },
    body: JSON.stringify({
      displayName: 'Audit Failure',
      email: 'audit-failure@example.test',
      phone: '+15551239999',
    }),
  });

  expect(response.status).toBe(500); // current behavior
  const row = database
    .prepare(`SELECT id FROM demo_signups WHERE email = ?`)
    .get('audit-failure@example.test');
  expect(row).toBeTruthy(); // state committed before the callback failed
});
```

For the reaper variant, insert an already-expired signup, call
`reapSignups(database, now, () => { throw new Error('down'); })`, and observe that it
throws and leaves the row in place.

The asynchronous variant can be reproduced with:

```ts
onSignupEvent: async () => {
  await Promise.resolve();
  throw new Error('async audit failure');
},
```

The callback type accepts it, the request does not await it, and the rejection is outside
the route's error handling.

### Why current tests miss it

The lifecycle test passes a synchronous sink that only pushes into an array. No test uses
a throwing or asynchronous sink, and no test asserts that a committed transition remains
usable when observation fails. The reaper test also uses an array-push sink that cannot
fail.

### Recommended remediation

Choose and document one of these policies:

1. **Best-effort observation — recommended for the demo API as currently shaped.**
   Accept `(event) => void | Promise<void>`, centralize calls in an async safe emitter,
   await the callback, catch failures, and log them without changing the route result.
   This should mirror `LocalWebAuthn.#emit`.
2. **Audit delivery is required for the state transition.** Move the event into a durable
   outbox written in the same database transaction as the transition, then deliver it
   asynchronously. A callback invoked after a committed write cannot provide this
   guarantee and should not make the request appear rolled back.

For `signup.reaped`, decide explicitly whether a failed audit write should retain personal
data. If yes, the audit record needs durable acknowledgement; if no, log the callback
failure and finish deletion. Do not rely on a synchronous callback's absence of throws as
the durability boundary.

### Required regression tests

- A synchronous throwing sink does not turn successful signup start/proof/claim into 500.
- An asynchronous sink is awaited; a rejection is contained and logged.
- Event ordering remains start → proof → completion → claim for a working sink.
- The chosen reaper policy is explicit and tested on sink failure.
- No unhandled rejection is produced by an asynchronous sink.

## 2. The signup cancellation audit stream is not faithful to committed state

**Severity: medium — audit correctness and incident response**

**Status: fixed on `fix/telemetry-state-fidelity`**

### Resolution

- `cancelSignup` returns whether its conditional update changed exactly one row. The
  channel route emits only for `true`, so repeat and too-late cancellations retain the
  existing idempotent API response without inventing an applied transition.
- `cancelActiveRecoveries` uses `UPDATE ... RETURNING id` and returns every affected
  signup ID. The credential-authentication handler emits one event per returned ID and
  emits nothing when the update changed no rows.
- `signup.canceled` now carries a `cause` of either `channel_proof` or
  `credential_authenticated`, making the two real veto paths distinguishable.
- Both emission paths use the protected sink after the update. Telemetry failure cannot
  undo or fail an already-applied cancellation, and a retry does not emit duplicates
  because the conditional update returns no IDs.

### Finding

The public cancel route judges the OTP, calls `cancelSignup`, unconditionally emits
`signup.canceled`, and returns `{ canceled: true }`:

```ts
const outcome = await verifySignupProof(...);
if (!canCancelSignup(outcome)) { /* reject */ }
const canceledAt = Date.now();
cancelSignup(database, signup.id, canceledAt);
emit({ type: 'signup.canceled', at: canceledAt, signupId: signup.id });
return context.json({ canceled: true });
```

But `cancelSignup` is a conditional update:

```sql
UPDATE demo_signups SET canceled_at = ?
WHERE id = ? AND canceled_at IS NULL AND enrollment_token IS NULL
```

It returns `void`, so the route cannot tell whether it changed a row. Two reachable no-op
cases are accepted by `canCancelSignup`:

- `verifySignupProof` returns `canceled` for an already-canceled row, and
  `canCancelSignup('canceled')` is true. Every replay emits another cancellation event.
- `verifySignupProof` returns `completed` for a completed plain signup. Its
  `enrollment_token` is non-null, so the update is a no-op, but the route reports and logs
  a cancellation while the enrollment token remains claimable.

This is not merely duplicate telemetry. An operator reading the new lifecycle stream can
conclude that a live enrollment was vetoed when it was not.

The inverse gap also exists. `credential.authenticated` calls
`cancelActiveRecoveries`, which updates every live recovery for the user's email and
returns only a count. The result is ignored and no `signup.canceled` events are emitted.
Those are real applied cancellations, but the lifecycle stream contains only the
credential-authentication event and cannot identify which signup rows changed.

Together these contradict the changelog claim that the demo emits at every applied
transition, including the veto: it emits some vetoes that did not apply and omits others
that did.

### Deterministic reproduction: false cancellation after completion

Extend the existing self-serve signup test in
`examples/demo/tests/application.test.ts`:

2. Start a plain signup and prove both channels, retaining either valid OTP.
3. Confirm the response contains an enrollment token.
4. POST the retained OTP to `/api/signup/cancel`.
5. Read `canceled_at` and `enrollment_token` from `demo_signups`.

Current behavior is:

```ts

expect(row.canceled_at).toBeNull();
expect(row.enrollment_token).not.toBeNull();

```

The response and event say canceled; the database says it was not.

For the duplicate case, cancel a pending recovery twice with the same valid OTP. The
second proof returns `canceled`, `canCancelSignup` accepts it, and a second identical
`signup.canceled` event appears even though `canceled_at` did not change.

### Deterministic reproduction: missing passkey-sign-in cancellations

The existing test named “any valid channel OTP vetoes a recovery, and a passkey sign-in
vetoes it too” already proves the database transition. Add an `onSignupEvent` collector,
start two active recoveries for the same client email, invoke the existing
credential-authentication path (or call the handler through a real sign-in), and assert:

```ts

// Current behavior: applied rows, no per-signup audit event.
```

Calling `cancelActiveRecoveries` directly is enough to expose the storage/API problem: it
returns a number, not the IDs required to emit correlated lifecycle events.

### Why current tests miss it

- The lifecycle test exercises one cancel request, not a no-op or repeated cancel.
- The recovery veto test checks database state but does not capture signup events.
- `cancelSignup` returns no row count, so no caller can assert that the emitted event
  corresponds to an applied transition.

### Recommended remediation

1. Make `cancelSignup` return `boolean` (or the canceled signup ID) based on
   `run(...).changes === 1`.
2. Emit `signup.canceled` only when that result says the update committed.
3. Preserve idempotent API behavior if desired, but distinguish “already canceled” and
   “too late to cancel” internally. Do not emit a fresh applied-transition event for
   either.
4. Change `cancelActiveRecoveries` to return the affected signup IDs. SQLite supports
   `UPDATE ... RETURNING id`; alternatively perform select/update in one immediate
   transaction.
5. Route those IDs through the same configured signup event sink. `createDemoAuthentication`
   currently does not receive that sink, so compute the sink once in
   `createDemoApplication` and share it with both the authentication event handler and
   `mountSignupRoutes`.

If `signup.canceled` is intended as an _attempt_ rather than a committed transition,
rename it and add a result. That would be a larger semantic change and would not close the
missing passkey-sign-in events by itself.

### Required regression tests

- First successful cancel emits exactly one `signup.canceled` and stamps `canceled_at`.
- Repeating the same cancel remains idempotent and emits no second applied event.
- Canceling after a plain signup has issued its token does not claim that the live token
  was canceled.
- Passkey sign-in cancellation emits one event per affected recovery ID.
- A sign-in with no active recovery emits no signup cancellation event.

## 3. The passkey-created notice invents an enrollment-link compromise

**Severity: medium — security-message correctness**

**Status: fixed on `fix/telemetry-state-fidelity`**

### Resolution

- `credential.registered` now includes the `createdVia` provenance already used for the
  durable credential row: `'enrollment'` or `'credential'`.
- The email and SMS templates require that provenance. Enrollment-authorized copy names
  an enrollment invitation without claiming how it leaked; session-authorized copy names
  a signed-in session and never mentions an enrollment link.
- Both paths tell the recipient to lock the account and revoke the new credential and
  live sessions before investigating the relevant authority. The templates now call the
  object a credential, so service credentials are not mislabeled as passkeys.
- Notification execution remains inside `LocalWebAuthn`'s protected event dispatch. A
  throwing or rejecting host handler is logged by `#emit` after registration commits and
  cannot fail `verifyRegistration`.

### Finding

`LocalWebAuthn.verifyRegistration` emits `credential.registered` after every successful
registration. That includes both authorization paths:

- a first credential authorized by an exchanged enrollment grant; and
- an additional credential authorized by an existing authenticated session.

The new demo handler sends `passkeyCreatedEmail` and `passkeyCreatedSms` for every one of
those events. The templates always say:

> If it was NOT you, someone else has used your enrollment link, which means they may
> control your email or your phone.

That statement is false on the session-authorized path. A user can legitimately add a
second passkey while signed in without any enrollment link. An attacker with a stolen
session can do the same. In the latter case, the recommended response focuses on email and
phone while omitting the compromised session and other live sessions that actually
authorized the registration.

The service already knows the provenance when it constructs `NewCredential.createdVia`:
`'enrollment'` when `authorization.grantId` is non-null, otherwise `'credential'`. The
event discards that fact. The template therefore cannot make the strong claim it makes.

This affects API credentials too. The demo changes the label to “service credential”, but
the subject and body still call it a passkey and still assert use of an enrollment link.
The important correctness issue is provenance, not terminology: the message states an
incident mechanism it has not established.

### Deterministic reproduction

The root suite already contains the service test “registers an additional passkey
authorized by an authenticated session.” Extend that scenario or add a demo-level variant:

1. Enroll and register credential A.
2. Use A's session token to call `registrationOptions` and `verifyRegistration` for B.
3. Capture the `credential.registered` event for B.
4. Render the notice the demo sends for that event.

Current behavior:

```ts
expect(registeredEvent.type).toBe('credential.registered');
// There was no enrollment grant for B, but the event has no provenance field.
const notice = passkeyCreatedEmail({
  appName: 'Example',
  label: 'passkey',
  supportContact: 'support',
});
expect(notice.text).toContain('used your enrollment link');
```

The test needs no attack simulation. The normal “add a passkey while signed in” path is
enough to prove the sentence false.

### Why current tests miss it

- The template test asserts message ordering and the benign “If that was you” branch, but
  supplies no provenance because the template accepts none.
- The service test proves the session-authorized registration path and its event, but does
  not pass that event through the demo's notification handler.
- The demo handler tests are concerned with authentication behavior, not captured notice
  content.

### Recommended remediation

There are two sound options:

1. **Make the notice provenance-neutral — smallest fix.** Say that a new credential was
   added and, if unexpected, instruct the person to contact support, lock the account,
   revoke the new credential and live sessions, then investigate enrollment links and
   bound channels. Do not assert which authority was stolen.
2. **Carry provenance in the event.** Split the credential event union so
   `credential.registered` includes `createdVia`, and optionally `grantId` or
   `parentCredentialId` only if those are appropriate for host audit. Render different
   copy for enrollment and session authorization. The service has the needed value at
   emission time.

Even with provenance, incident copy should avoid claiming email or phone compromise merely
because an enrollment token was used: a token can leak through forwarding, clipboard
history, browser state, or another channel. “Re-secure every bound channel” can be prudent
advice without presenting it as a proven cause.

### Required regression tests

- A session-authorized registration notice does not mention an enrollment link.
- Its remediation includes revoking the unexpected credential and live sessions.
- An enrollment-authorized notice may mention the enrollment link only when provenance is
  explicitly supplied.
- The benign reading remains first for expected registrations.
- Email and SMS carry materially equivalent, provenance-correct advice.

### Files likely to change

- `packages/server/src/types.ts` if provenance is added to the event
- `packages/server/src/service.ts` if provenance is added to the event
- `examples/channels/src/templates.ts`
- `examples/channels/tests/channels-core.test.ts`

## 4. An optional undiagnosing store still produces `enrollmentState: 'unknown'`

**Severity: low — API contract and migration-document correctness**

**Status: fixed on `fix/telemetry-state-fidelity`**

### Resolution

- `#refusedEnrollment` now distinguishes a missing diagnostic method from an implemented
  method returning explicit `unknown`.
- The best-effort `enrollment.rejected` event still reports `state: 'unknown'` and
  `userId: null` when no diagnosis is possible, preserving useful refusal telemetry.
- The thrown `LocalWebAuthnError` receives `enrollmentState` only when the store performed
  a diagnosis. Its optional class field is type-only, so an undiagnosed error has no own
  `enrollmentState` property at runtime.
- The existing protected `LocalWebAuthn.#emit` boundary contains any failure from the
  rejection telemetry handler, so diagnosis and refusal semantics are unaffected.

### Finding

The new store method is deliberately optional:

```ts
enrollmentGrantState?(
  tokenHash: Uint8Array,
  now: number,
): Promise<EnrollmentGrantRejection>;
```

`docs/MIGRATING.md`, the store TSDoc, and `LocalWebAuthnError.enrollmentState` TSDoc all say
that a custom store which omits the method keeps the previous behavior: one
`invalid_enrollment` error with no state attached.

`LocalWebAuthn.#refusedEnrollment` instead substitutes an unknown diagnosis:

```ts
const rejection = (await this.#store.enrollmentGrantState?.(tokenHash, now)) ?? {
  state: 'unknown' as const,
  userId: null,
};
// ...
return new LocalWebAuthnError(
  'invalid_enrollment',
  'The enrollment link is invalid or expired.',
  403,
  { enrollmentState: rejection.state },
);
```

The resulting error always has `enrollmentState: 'unknown'` on this failure path, even
when the store did no diagnosis. The demo forwards any truthy state in its JSON error and
the browser package accepts and exposes `unknown`, so the difference can cross the HTTP
boundary.

The existing test exposes the contradiction. It is named “leaves the state off when the
store cannot diagnose”, but asserts `enrollmentState: 'unknown'` rather than asserting
`undefined`.

This is unlikely to break authorization, but it invalidates the explicit migration promise
made to custom-store authors and makes “the official store looked and found no row”
indistinguishable from “this store has no diagnostic capability.”

### Deterministic reproduction

Run the existing test in `tests/server/service.test.ts` or reduce it to:

1. Wrap an official store in the existing proxy that returns `undefined` for
   `enrollmentGrantState`.
2. Issue and successfully exchange one token.
3. Present the same token again.
4. Inspect the caught `LocalWebAuthnError`.

Current behavior:

```ts
expect(error.code).toBe('invalid_enrollment');
expect(error.enrollmentState).toBe('unknown');
```

Documented behavior:

```ts
expect(error.enrollmentState).toBeUndefined();
```

### Recommended remediation

Honor the compatibility promise. Distinguish “method absent” from “method returned
unknown”:

- keep `rejection = { state: 'unknown', userId: null }` for the
  `enrollment.rejected` audit event, whose type requires a state and for which unknown is
  honest;
- attach `enrollmentState` to `LocalWebAuthnError` only when
  `enrollmentGrantState` was actually implemented and called.

The alternative is to keep the implementation and change every contract statement to say
that omission yields `unknown`. That is technically coherent, but it abandons the stated
backward-compatibility property for no functional gain.

### Required regression tests

- A store without `enrollmentGrantState` yields an error with no `enrollmentState` own
  property.
- The same refusal still emits `enrollment.rejected` with `state: 'unknown'` and
  `userId: null`.
- An official store with no matching row yields an error with explicit
  `enrollmentState: 'unknown'`.
- The demo/browser round trip preserves the distinction between absent and explicit
  unknown.

Rename the current test so its title and assertion agree.

### Files likely to change

- `packages/server/src/service.ts`
- `tests/server/service.test.ts`
- `packages/server/src/errors.ts` only if TSDoc needs clarification
- generated `packages/server/dist/*` artifacts
- `docs/MIGRATING.md` if a different compatibility decision is chosen

## 5. A finished challenge delays grant cleanup by one complete sweep

**Severity: low — cleanup contract and retention accounting**

**Status: fixed on `fix/telemetry-state-fidelity`**

### Resolution

- SQLite, D1, and PostgreSQL now delete finished challenges before expired grants in the
  same transaction or D1 batch.
- The grant query still protects rows referenced by a live challenge. Once a challenge is
  consumed or expired, both it and its already-expired grant are removed and counted in
  one sweep.
- Cleanup itself has no telemetry callback. Hosts can report the resolved `CleanupResult`,
  whose `challenges` and `enrollmentGrants` counts now faithfully describe the same sweep;
  a host reporting failure cannot change the completed cleanup result.

### Finding

All three adapters perform cleanup in this order:

1. sessions;
2. enrollment grants;
3. challenges;
4. DPoP proofs;
5. DPoP nonces.

The grant delete protects referential integrity with:

```sql
DELETE FROM localwebauthn_enrollment_grants
WHERE expires_at <= ?
  AND id NOT IN (
    SELECT grant_id FROM localwebauthn_challenges WHERE grant_id IS NOT NULL
  )
```

The next statement deletes every expired or consumed challenge. Therefore an expired
grant referenced by a challenge which this same cleanup is about to delete is skipped on
the first pass. The challenge is removed, the transaction commits, and the grant remains
until the next scheduled cleanup. With the examples' five-minute interval, retention and
`CleanupResult.enrollmentGrants` lag by up to another five minutes.

This is common on the real service path: registration and authentication challenges are
consumed before verification finishes. The new conformance test “keeps a spent grant until
its window closes, then reaps it” calls `completeRegistration` with a constructed consumed
challenge value but does not persist a corresponding challenge row. It therefore cannot
exercise the foreign-key/order interaction and passes after one cleanup.

### Deterministic reproduction on any official store

record helpers. The exact values are illustrative:

  idHash: bytes(23),
  kind: 'registration',

### Recommended remediation

Delete finished challenges before expired grants. The grant query will still protect any
grant referenced by a _live, unconsumed_ challenge because that row remains in the
subquery. Consumed and expired challenge rows disappear first, allowing their already
expired grants to be reaped in the same transaction/batch.

If statement order is intentionally fixed for another invariant, run the grant delete a
second time after challenge cleanup and add both row counts. Reordering is simpler and
avoids an unnecessary statement.

Review the lifetime relationship between grant expiry, enrollment-session expiry and
challenge expiry while making this change. The regression fixture above puts all three
dead before cleanup, so it tests only the unambiguous case and does not force deletion of
a grant still needed by a live challenge.
