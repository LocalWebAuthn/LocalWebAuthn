## Accepted fixes and invariants to preserve

### D1 version-aware migration

packages/server/src/d1.ts now:

- creates the migration table before reading its version;
- treats version zero as a fresh install;
- obtains the required DDL from localWebAuthnUpgradeStatements;
- applies the DDL and current-version insertion in one D1 batch;
- re-reads the installed version after a concurrent duplicate-column loser;
- deletes the misleading unused localWebAuthnMigrationStatements helper.

The Miniflare tests construct the literal released-v1 DDL, preserve representative rows,
compare fresh and upgraded object names, inspect the re-scoped grant index, verify v2
columns, run the migration repeatedly and exercise the upgraded store.

This matches Cloudflare's current contract: D1 batch statements execute as a SQL transaction
and a failing statement aborts or rolls back the sequence.

Primary reference:
https://developers.cloudflare.com/d1/worker-api/d1-database/

Do not restore the old non-atomic or orphan-credential narrative.

### DPoP proof-before-touch operation

packages/server/src/service.ts now exposes authenticateMachineRequest. It:

1. hashes and resolves the supplied session token without touching activity;
2. obtains the credential identity from that resolved session;
3. verifies the DPoP proof against the credential and exact token;
4. atomically claims the proof identifier;
5. touches the session only after proof verification;
6. fails if the session was concurrently revoked before the touch;
7. returns the derived identity and response nonce.

The token and resolved session cannot be mismatched because the caller supplies no separate
session object. The tests prove a bearer-only request does not extend idle life and that a
proof for one token cannot authenticate another.

Keep this method as the normal machine-route API.

### Fixed-point unscoped tree revocation

For an unscoped credential tree, the new root-first fixed-point loop composes correctly with
the store's conditional registration insert:

- a child committed before its authorizer is revoked is found on re-enumeration;
- a registration trying to commit after its authorizer is revoked fails the transactional
  authorization check;
- once every node in the tree is revoked, the tree can no longer grow.

Retain the deterministic test that inserts a child after the first descendant snapshot. It
is a valuable regression test even after a stronger fence is added.

### Runtime disclosure wording

SECURITY.md now correctly distinguishes:

- database-at-rest disclosure, where stored digests and public keys do not directly
  authenticate;
- live process, tracing and crash-dump exposure, where raw bearer values can be observed.

Retain the host redaction guidance for Authorization, Cookie, Set-Cookie, enrollment values,
URL fragments and authentication response bodies.

## 1. Release blocker: normative DPoP examples still teach the unsafe path

### Observed state

README.org still says:

> Server side, the machine guard is resolveSession plus one call

It then calls verifyDpop with resolved.session. The omitted or preceding resolveSession call
touches lastSeenAt by default. A holder of only the bearer token can therefore keep the
session alive even though the subsequent proof check fails. This is the precise defect
authenticateMachineRequest was introduced to close.

docs/MIGRATING.md also presents verifyDpop as the normal host integration. README-DETAIL.org
and SECURITY.md recommend authenticateMachineRequest, so the repository currently gives two
contradictory integration patterns.

The status in docs/REVIEW-20260809.md marks the code issue resolved, but the public
documentation issue is not resolved while the primary README demonstrates the old sequence.

### Required resolution

Replace the README machine guard with one complete operation:

```ts
const authenticated = await auth.authenticateMachineRequest({
  sessionToken: token,
  proof: request.headers.get('DPoP') ?? undefined,
  method: request.method,
  url: request.url,
  requireNonce: true,
});

if (authenticated.session.credentialKind !== 'service') {
  return forbidden();
}
```

The example must also show:

- exact extraction of the raw token;
- generic handling of every non-nonce DPoP authentication failure;
- the RFC 9449 use_dpop_nonce response through dpopChallenge;
- the server-derived credential-kind check;
- attachment of the returned current nonce on successful responses;
- no resolveSession call before authenticateMachineRequest.

Update docs/MIGRATING.md to introduce authenticateMachineRequest as the new safe service
API. verifyDpop may be documented afterward as a lower-level primitive, not as the migration
target.

### API hardening options

**Option A — minimum: documentation and deprecation**

- Keep verifyDpop public.
- Mark it advanced in generated declarations and package documentation.
- Add a deprecation note steering all route integrations to authenticateMachineRequest.
- State that the caller must resolve without touch and preserve exact token/session pairing.

**Option B — stronger: rename the unsafe primitive**

Rename it to verifyDpopForResolvedSessionUnsafe or place it under an advanced entry point.
This is a v3 major release, so now is the least costly time to make the hazard visible in the
name.

**Option C — strongest default surface**

Stop exporting the session-taking primitive from the default server entry point. Export
only authenticateMachineRequest and lower-level stateless cryptographic verification that
accepts an explicit public key rather than a mutable session identity.

Recommended: Option A immediately, with Option B if the public API can still change before
v3.

### Additional hardening

authenticateMachineRequest proves possession but does not itself restrict credential kind.
The demo checks SERVICE_KIND after authentication. Consider accepting an optional
allowedCredentialKinds input and rejecting a disallowed kind before touching the session.
This is not required to close the original DPoP bug, but it would let the same fail-closed
operation enforce both route authentication and its server-owned credential-class boundary.

### Required tests

- Add a compiled or typechecked version of the README machine middleware.
- Assert the recommended middleware makes no resolveSession call.
- Assert missing/bad proof does not change lastSeenAt.
- Assert the exact nonce challenge headers are returned.
- Assert a wrong credential kind is rejected, preferably before touch if kind filtering is
  added.
- Search normative docs in CI and fail on the old resolveSession-plus-verifyDpop pattern.

- README-DETAIL.org
- docs/MIGRATING.md
- packages/server/src/service.ts public documentation
- packages/server/src/index.ts if exports change

## 2. Release blocker: scoped revocation has no registration fence

### What the fixed-point loop solves

The deterministic new test stages a child registration after the first subtree snapshot and
before root revocation. Re-enumeration finds that child. This closes the original one-snapshot
failure for an unscoped tree whose authorizing root is revoked.

### What it does not solve

The helper is also used by:

- revokeCredentialTree with a kinds filter;
- revokeUserAuthentication with kinds.

Those operations deliberately leave some credentials active. If a spared credential is
allowed to register a selected kind, it can create a new selected-kind credential after the
terminal enumeration but before the method returns. That requires one registration in the
terminal window, not necessarily winning all 64 passes.

The same conceptual problem persists after return: if the authority that remains active is
itself compromised and still permitted to create the revoked kind, no one-shot scoped
cleanup can keep that kind absent. The scope is insufficient for that incident.

The security guarantee must therefore distinguish:

- revoking all registration authorities relevant to the compromise;
- removing a selected class while deliberately retaining authorities that may create it
  again.

### Non-convergence is currently reported as success

The helper stops after 64 progressing passes, logs a warning and returns its list. The public
effects then look successful:

- revokeCredentialTree returns normally;
- scoped revokeUserAuthentication returns void;
- user.authentication_revoked is emitted.

A security-sensitive caller cannot tell whether remediation converged. A logger warning is
not a fail-closed API.

### Recommended design: an explicit registration fence

An epoch alone invalidates challenges issued before the bump, but does not stop a surviving
authority obtaining a new challenge after the bump while remediation is still running. Use
an epoch together with an active fence.

One workable representation is a registration-fence table keyed by:

- user ID;
- a global or credential-kind scope;
- monotonically increasing generation;
- blocked state and timestamp.

Registration challenges capture both:

- the current user-global generation;
- the current target-kind generation.

The transaction that inserts a credential must require:

- neither applicable fence is blocked;
- both challenge generations still equal the current generations;
- the authorizing grant/session and credential are still active.

Scoped remediation then has a linearization point:

1. Atomically set the applicable fence blocked and increment its generation.
2. Revoke pending grants and credentials to a fixed point.
3. Verify that no active selected credentials remain.
4. Atomically clear the same fence only if its generation still matches the remediation
   token.
5. Return success.

Any challenge issued before the fence is stale. No challenge may be issued or completed
while blocked. A registration after the fence is cleared belongs to the post-remediation
state rather than racing the cleanup.

For unscoped tree revocation, revoking the root authority remains a natural fence and may
not need a user-wide block. For a kind-scoped subtree, a conservative user-and-kind fence is
simpler than a per-tree generation and may briefly block unrelated registration of that
kind.

### Failure behavior

- If enumeration or storage fails, leave the fence blocked and return an explicit error.
- If the pass limit is reached, throw revocation_not_converged and do not emit a success
  event.
- Emit a separate remediation-failed audit event with user, scope and generation, but no
  secrets.
- Provide an explicit administrator operation to inspect and clear a stuck fence after
  remediation is retried.
- Cleanup must not automatically clear a fence merely because it is old; failure should be
  safe rather than silently reopening registration.

### Alternative if a schema fence is deferred

Narrow the API contract:

- Call unscoped tree/account operations remediation.
- Call scoped operations best-effort administrative revocation.
- Require the host to suspend registration for the affected user before calling them.
- Accept a host-supplied fence callback or token and verify it before returning.
- Return convergence status rather than void.

Do not say a concurrent credential is always caught. Say the current implementation catches
credentials visible on a later pass and depends on an external fence for an absolute scoped
guarantee.

### Required tests

Tests must be deterministic rather than timing-based:

1. Existing child-after-first-snapshot unscoped tree test remains.
2. A spared person credential attempts to create a service credential during scoped
   revokeUserAuthentication.
3. A spared root attempts to create a selected-kind child during a kind-filtered tree revoke.
4. A challenge issued before fence activation cannot complete afterward.
5. registrationOptions is refused while the applicable fence is blocked.
6. A challenge issued after fence clearance can complete.
7. A stale remediation token cannot clear a newer fence.
8. Reaching the pass bound returns or throws an explicit incomplete result.
9. No success audit event is emitted after incomplete remediation.
10. A simulated crash/error leaves the fence closed.

Run the same store-level invariants for SQLite, PostgreSQL and D1. Service-level race tests
may use store proxies to place barriers, but each adapter also needs conformance coverage for
the fence compare-and-swap.

## 4. Release blocker: private-key claims still cross the wrong component boundary

### Observed contradiction

README.org says:

> LocalWebAuthn never possesses private key material. Not on the server, not in either client
> package ... There is no moment in any flow at which a private key passes through code in
> this repository.

The optional implementation does:

- packages/client/src/keystore.ts generate an extractable key pair;
- export PKCS#8 into an ArrayBuffer and base64 string;
- import caller-supplied private-key base64 through mutable buffers and WebCrypto;
- examples/demo/src/client.ts keep the credential text in application state;
- render it for clipboard and download.

SECURITY.md similarly says keys live in places that are not this package, then says
@localwebauthn/client reads the script key and holds it in process memory.

The narrow security property remains true and valuable:

> LocalWebAuthn server-side persistent state contains no credential private-key material.

The repository-wide transient-possession wording is not true.

### Minimum documentation resolution

Use one component-specific statement consistently:

> @localwebauthn/server never receives or persistently stores credential private keys; it
> stores public credential material and one-way token digests. Browser-mediated human
> passkeys remain under their authenticator or provider. Optional software-key and
> provisioning components may transiently process exportable private-key material, and
> operator-selected keystores may persist it outside LocalWebAuthn server state.

Remove or qualify:

- never possesses;
- no private key passes through repository code;
- exactly one copy;
- one copy in one place;
- DESTROYS or shreds unless a concrete external tool actually performs and guarantees it;
- universal Secure Enclave or non-exportability language.

WebCrypto does not guarantee erasure of key material after application references disappear.
Primary reference:
https://www.w3.org/TR/WebCryptoAPI/

### Recommended component split

Make the default client entry point operate on opaque signers:

- client/core — MachineKeyStore, software WebAuthn ceremony construction, DPoP proof
  construction and MachineClient;
- client/file-key or client/unsafe-exportable — PKCS#8 generation, import/export and
  credential-file helpers;
- client/platform-* — keychain, TPM, Secure Enclave, PKCS#11, signer agent or KMS adapters;
- demo provisioning — explicitly demo/compatibility-only browser export flow.

The default client export should not expose generateKeyStore or importKeyStore if the
project wants the core package to claim it never handles raw private bytes. Applications
that choose file-key support should import the boundary explicitly.

Add dependency rules so:

- server and browser packages cannot import raw-key modules;
- client core cannot import the exportable adapter;
- demo provisioning is the only browser bundle allowed to import export functions.

### Preferred provisioning flow

Generate the durable key on the target CLI machine:

1. A fresh human passkey session issues a short-lived, single-use service enrollment.
2. The human transfers the enrollment capability, not the durable key.
3. The CLI generates its key through the selected MachineKeyStore.
4. The CLI performs registration and proves possession.
5. Only public credential material reaches the server.
6. The destination keystore persists an opaque handle or file according to operator policy.

Add a high-level client enroll operation that owns the full exchange/options/verify
sequence. The enrollment capability remains a bearer secret and needs expiry, single-use
consumption, scope binding and log redaction.

### If browser minting ships in v3

- Name it an exportable-key compatibility path.
- Serve it from a minimal dedicated origin or isolated bundle.
- Load no third-party JavaScript and register no service worker.
- Apply strict CSP, frame-ancestors none, Cache-Control no-store, restrictive referrer and
  permissions policies, and Trusted Types where supported.
- Do not copy or download by default.
- Warn about clipboard history, Downloads, backups, extensions and crash dumps.
- Keep the credential pending until the destination proves possession.
- Expire abandoned pending credentials.
- Revoke the registration-created session if it is not returned to the destination.
- Clear mutable buffers as best effort only; never claim guaranteed zeroization.

### Required tests

- The default client entry point contains no raw private-key export operation.
- Package boundary tests reject imports from forbidden layers.
- Target-side enrollment activates only after proof of possession.
- Expired, reused and revoked enrollment capabilities fail.
- An abandoned browser-minted credential remains inactive.

## 5. High priority: MachineClient cannot distinguish a rejected request from an arbitrary 401

### Observed behavior

packages/client/src/machine-client.ts sends the request, and after any 401:

- captures any DPoP-Nonce header;
- clears the session only when that header is absent;
- sends the same path and RequestInit again.

It does not require:

- a WWW-Authenticate DPoP challenge;
- error=use_dpop_nonce;
- any other positive indication that authentication rejected the request before dispatch;
- a replayable request body;
- a body factory for a one-shot request body.

The distinction matters:

- An exact DPoP use_dpop_nonce challenge is produced by authentication middleware before the
  application handler runs. The operation has not executed, so retrying it with a fresh proof
  is safe regardless of whether its HTTP method is normally idempotent.
- An expired-session rejection is equally safe to retry after reauthentication when the
  server contract guarantees that it was produced before application dispatch.
- An arbitrary application 401 carries no general guarantee that the handler performed no
  work. HTTP status alone is not proof of non-execution.

The current demo attaches DPoP-Nonce to successful authenticated responses before control
passes to the downstream handler. A downstream application 401 can therefore carry that
header even though it is not a DPoP nonce challenge. MachineClient currently sees the nonce
header, treats the session as still live, and repeats the request without checking
WWW-Authenticate. If the handler performed work before returning 401, that work can happen
twice.

Idempotency is not a requirement for retrying a genuine pre-dispatch DPoP or expired-session
rejection. It is relevant only if the client chooses to retry a response whose pre-dispatch
origin it cannot establish. The default client should not make that uncertain retry.

Body replayability is a separate mechanical issue even when the server definitely rejected
the operation. The first fetch has consumed or transferred a ReadableStream body before the
401 arrives, so a valid retry still needs a reconstructable body.

RFC 9449 nonce challenge reference:
https://www.rfc-editor.org/rfc/rfc9449.html

### Recommended retry model

Classify the response by authentication protocol, not by HTTP method:

1. Parse WWW-Authenticate case-insensitively and support multiple challenges.
2. Classify a response as a DPoP nonce rejection only when it contains the DPoP scheme,
   error=use_dpop_nonce and DPoP-Nonce.
3. Retry that rejected request once with the supplied nonce and a unique proof identifier.
   POST, PATCH and other methods do not need an idempotency restriction because the
   authenticated operation was never dispatched.
4. Give expired-session rejection an equally explicit pre-dispatch signal. This may be a
   documented WWW-Authenticate challenge, a dedicated LocalWebAuthn error code/header, or a
   protocol contract limited to known middleware responses.
5. Reauthenticate and retry once when that explicit expired-session signal is present.
6. Return an unclassified application 401 without retrying it. Do not infer non-execution
   from status alone or from an incidental DPoP-Nonce header.
7. Require a body factory, cloneable Request, or other reconstruction mechanism for a
   ReadableStream or one-shot body. Strings, byte arrays and other reusable bodies may be
   resent directly.
8. Bound nonce retry and reauthentication retry independently.
9. Cancel or consume the first response body before discarding it where the runtime needs
   that for connection reuse.

If the library exposes an override to retry an unclassified response, that override is where
an idempotency key or application-specific replay guarantee belongs. It is not needed on the
normal, positively classified DPoP path.

### Required tests

- An arbitrary downstream 401 is not automatically replayed.
- An incidental DPoP-Nonce alone is insufficient.
- An exact use_dpop_nonce challenge retries POST once with a fresh proof identifier.
- The protected POST handler executes exactly once: zero times before the challenge and once
  after the valid retry.
- Repeated nonce challenges stop at one retry.
- An explicitly classified expired-session rejection reauthenticates and retries POST, with
  the protected handler executing exactly once.
- An unclassified 401 does not trigger reauthentication and replay.
- Stream bodies require a factory and are never silently reused.
- Reusable string and byte-array bodies survive a classified retry unchanged.
- If an uncertain-retry override exists, its idempotency key is preserved.

## 7. Documentation claims still needing correction

### DPoP is not a complete HTTP message signature

Current README threat language says htm, htu and ath bind a captured proof to one request.
RFC 9449 excludes query and fragment from htu comparison and does not bind the request body.

Rewrite this as:

- proof of possession sender-constrains the session token;
- jti prevents accepted-proof replay;
- method and normalized URI are covered as defined by RFC 9449;
- TLS, application authorization and idempotency remain required;
- authorization-significant body/query distinctions are not protected by DPoP itself.

Use an application content digest or a suitable HTTP Message Signatures profile when exact
body integrity is required.

HTTP Message Signatures reference:
https://www.rfc-editor.org/rfc/rfc9421.html

### Human passkeys are not universally hardware-bound

Replace universal Secure Enclave/non-exportability wording with authenticator-mediated
language. WebAuthn permits hardware, software, roaming, platform and synced authenticators.
Backup-eligible credentials may be synchronized or recovered by their provider.

Primary references:

- https://www.w3.org/TR/webauthn-3/
- https://support.apple.com/en-euro/guide/security/sec1c89c6f3b/web
- https://support.apple.com/en-ie/102195

### Database disclosure wording

Nothing in stored state directly authenticates as a user, but the database still contains
PII, relationship metadata, public keys and timing information. Prefer non-authenticating
over nothing valuable or nothing sensitive.

### Competitor comparison

line counts, or generate them at release. Separate factual product comparisons from design
opinion and cite primary sources for third-party behavior.

## 8. Demo and credential lifecycle issues still open

### Registration-created service session is discarded

The demo's API-key verify route receives a session token created for the new service
credential, then drops it without revoking it. The row remains live until expiry.

Choose one:

- revoke the returned session immediately;
- return and use it as the destination's first session;
- add a service option that completes credential registration without creating an initial
  session.

The first is the smallest demo fix. The third is preferable if browser provisioning or
out-of-band registration commonly wants a credential without an immediate authenticated
session.

Add a test that provisioning does not leave a live unreachable session.

### Credential-file parsing and shell output

The file formatter assumes current base64 key material is shell-safe while the abstraction
permits arbitrary keystore references. A reference containing whitespace, quotes, command
syntax or control characters may not be safe to source.

Preferred:

- use JSON with documented mode 0600 permissions;
- treat shell export as an explicitly escaped compatibility format;
- quote every value with tested POSIX single-quote escaping;
- validate base URL, HTTPS/loopback policy, RP ID relationship, origin, base64url values,
  handle lengths, algorithm and keystore scheme;
- bound input file size and reject duplicate/ambiguous fields.

Add adversarial tests for quotes, spaces, dollar signs, command substitution text, newlines,
invalid base64url, userinfo URLs, Unicode hosts and non-HTTPS remote endpoints.
