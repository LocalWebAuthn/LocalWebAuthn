# Review: machine API credentials and credential kinds

Reviews `feature/machine-api-credentials` at `1a5e548`, against `main` at `35a40c0`.

The feature works and is well tested at the seams. The complexity is mostly warranted and
mostly opt-in. But the branch spends its budget unevenly: three of the eight categories
below carry complexity that buys little, one documented promise is now false, and the
newest security-critical module is the least tested code in the repository.

## Measurements

|                                            | Before | After           |          |
| ------------------------------------------ | ------ | --------------- | -------- |
| Package source (server + browser + client) | 4,149  | 7,076           | **+71%** |
| `LocalWebAuthnStore` methods               | 21     | 28              | +33%     |
| Public service methods                     | 13     | 19              | +46%     |
| Schema versions                            | 1      | 2               |          |
| Tests                                      | 91     | 171 + 9 + 4 e2e |          |

`SECURITY.md` says the package is "about 3,500 lines of TypeScript … so that a reviewer can
read the whole authentication path rather than trust it." It is now 7,076. **That claim is
load-bearing for the project's pitch and the branch silently broke it.**

Two costs are being conflated and should be separated. The _default-path behaviour_ barely
moved: a host that declares no `credentialKinds`, configures no `dpopNonce` and never sets
a `credentialKind` sees exactly two changes (the kind-scoped last-credential guard, and the
widest-idle window in `revokeUserSessions`). The _reading surface_ grew 71%. The first cost
is genuinely near zero; the second is real and unavoidable for anyone auditing.

## 1. Schema and migrations

Collapsing four development versions into one was right and the migration test — building
from the literal released v1 DDL out of git history, then asserting structural equivalence
with a fresh install — is the strongest correctness artifact on the branch.

One fragile spot:

```ts
const newTables = schema.filter((statement) =>
  /^CREATE (TABLE|INDEX|UNIQUE INDEX) IF NOT EXISTS localwebauthn_dpop/u.test(statement),
);
```

A table name is hard-coded into a filter. The next schema change that adds a table will
silently not create it on upgrade, and only a fresh install will work — the exact failure
shape as the `applied_at INTEGER` overflow, which also only appeared on a fresh database.

**Fix:** have each migration entry declare the table names it introduces, and filter the
schema by those names. Adding a table then means adding its name next to the ALTERs, in the
place a reader is already looking, rather than remembering a regex two functions away.

```ts
{ version: 2, statements: [...], newTables: ['localwebauthn_dpop_proofs', 'localwebauthn_dpop_nonces'] }
```

Also note the review-visible hazards the schema now carries, both already documented but
both discovered the hard way: no `--` comments (the splitter collapses whitespace and
comments out the following statement), and no new `CHECK` constraints (SQLite cannot ALTER
one in, so fresh and upgraded would diverge).

## 2. The store contract: 21 → 28 methods

Seven new methods, each individually justified, but the contract is what a custom store
implementer must satisfy and it is now 28 methods. Three of the seven exist only to serve
optional features (`claimDpopProof`, `claimDpopNonce`, `dpopNonces`), and a host that will
never use DPoP must still implement them or fail to typecheck.

**Fix:** split the contract. `LocalWebAuthnStore` keeps the 21 that every deployment needs;
`LocalWebAuthnDpopStore` carries the three DPoP methods and is required only when
`dpopNonce` or `verifyDpop` is used. The service can check for the methods at the point of
use and throw `invalid_configuration` with a clear message, which is strictly friendlier
than a compile error about a method the host has no interest in.

`revokeLiveCredentialSessions` and `revokePendingEnrollmentGrants` are both service-layer
loop helpers introduced to avoid variable-length `IN (...)`. That trade was right — dynamic
SQL leaving `queries.ts` would be worse — but it should be said out loud that it costs one
round trip per credential.

## 3. Per-kind session durations — cut this

The strongest simplification available. `credentialKinds[kind].sessionAbsoluteMs` and
`.sessionIdleMs` cost, between them:

- `#widestIdleMs` computed in the constructor;
- a **second liveness check in `resolveSession`**, the hottest path in the package, because
  the store must filter on the widest window before the kind is known;
- a config clamping rule with its own error case (`sessionIdleMs` inherited vs explicit),
  which a test had to discover;
- a divergence class: `revokeUserSessions` was computing liveness from the _global_ window
  and would have left a longer-windowed session alive after "sign out everywhere". Found and
  fixed, but it was created by this feature.

What it buys: machine sessions can expire sooner than human ones. But the machine client
re-authenticates on `401` for two round trips, so a host can get the same effect by simply
setting a short global `sessionAbsoluteMs`, or by not caring.

**Fix:** drop `sessionIdleMs` per kind entirely, and keep `sessionAbsoluteMs` — which needs
_no_ `resolveSession` change at all, because absolute expiry is stamped on the row at
creation. That deletes `#widestIdleMs`, the second liveness check, the clamping rule and
the divergence class, for no loss a host would notice.

## 4. Dual-path bulk revokes

`revokeUserSessions` and `revokeUserAuthentication` each have a scoped and an unscoped
implementation reaching different SQL. That structure is what produced the bug where the
scoped `revokeUserAuthentication` left pending grants alive — a live grant of a revoked
kind being standing authorization to re-enroll straight back in.

Two behaviours that are supposed to agree, implemented twice, is the shape that generates
that class of bug. It will generate another.

**Fix:** make the unscoped path a special case of the scoped one — enumerate the distinct
kinds present for the user and pass them — so one implementation serves both. If the extra
query is unwelcome on the unscoped path, keep both but add a test that asserts they agree
for a single-kind user, which is cheap and would have caught the grant divergence.

## 5. DPoP verification — the weakest spot on the branch

`packages/server/src/dpop.ts`: **70.2% statements, 64.9% branches.** The lowest of any
module, and it is the newest security-critical verification code.

28 uncovered statement lines. Against the rejection reasons, the untested ones are:

`malformed_proof`, `malformed_header`, `unexpected_typ`, `unsupported_alg`, `missing_jwk`,
**`private_key_in_jwk`**, `unsupported_credential_key`, `malformed_jwk`,
`malformed_signature`, `bad_signature`, `malformed_payload`, `bad_jti`, `bad_iat`

Tested: `key_mismatch`, `htm_mismatch`, `htu_mismatch`, `ath_mismatch`,
`iat_out_of_window`, `use_dpop_nonce`.

So roughly twelve of fifteen ways to reject a proof have never been exercised — including
`private_key_in_jwk`, which exists specifically as a key-confusion guard. A verifier whose
rejection paths are untested is a verifier whose _acceptance_ is unproven: nothing
demonstrates it rejects for the reason claimed rather than incidentally.

`coseToJwk` has three uncovered paths of its own: malformed COSE (line 79), the EC2
validation failure (93), and **the entire OKP/Ed25519 branch (97–105, zero hits)**. `EDDSA`
is an exported constant in `@localwebauthn/client` and the Ed25519 path is unexercised in
**both** packages — no test has ever run it.

**Fix, and this is the highest-value change in the review:** one table-driven test over
every reason string. ~40 lines, takes `dpop.ts` to near-100%, and each case documents a
rejection the code promises.

```ts
for (const [reason, mutate] of Object.entries(corruptions)) {
  it(`rejects ${reason}`, async () => {
    expect(await verifyDpopProof(mutate(await validInput()))).toMatchObject({
      valid: false,
      reason,
    });
  });
}
```

**And:** either add one Ed25519 round-trip test in each package, or stop exporting `EDDSA`.
Shipping an algorithm constant whose code path has never run is a claim the branch has not
earned.

## 6. Host ergonomics

Three warts, all cheap to fix while the API is unreleased.

**None of the new types are exported.** `index.ts` is untouched, so a host cannot name
`CredentialKindPolicy`, `CredentialProvenance`, `RegistrationOptionsInput` or
`AuthenticationOptionsInput`. Writing a typed wrapper around `registrationOptions` is
currently impossible without reaching into `dist/types-*.d.ts`. **This is a hard defect,
not a style question.**

**`issueEnrollment(userId, string | { … })`** takes a union for backwards compatibility with
a signature that was never released, so the compatibility buys nothing. Collapsing it to the
options object touches 10 sites across 8 files — two in `examples/`, the rest tests — since
every other caller passes no second argument at all. More churn than it looks, all
mechanical, and worth doing while the alternative is a union a reader has to destructure
mentally.

**The nonce challenge is a four-step protocol in every host:** catch `dpop_nonce_required`,
call `dpopNonce()`, set `DPoP-Nonce`, set `WWW-Authenticate`. That is four things to get
right, repeated per host, for one RFC behaviour — precisely the situation `authCookieNames`
and `cookieAttributes` already exist to prevent. Add `dpopChallenge()` to `http.ts`
returning the header pair, or have `verifyDpop` return `{ ok: false, challenge: {…} }`
instead of throwing for that one case.

## 7. Tests

The seam coverage is good and the choices were right: real ceremonies rather than mocked
ones, the real released v1 DDL, conformance across all three adapters, and a Playwright run
that drives the actual CLI against the actual server. Four bugs were caught by tests during
the build — the config clamp, the `--` comment, the `applied_at` overflow, and the
duplicate revoke button — which is the system working.

Gaps, in priority order:

1. `dpop.ts` rejection paths (above).
2. Ed25519, both packages (above).
3. `config.ts` at 75.9%: the per-kind normalization error branches. Moot if durations are cut.
4. No test asserts the scoped and unscoped revokes agree (above).
5. `revokeCredentialTree` ignores `kind` entirely. In the demo every API credential's parent
   _is_ the person's passkey, so revoking that subtree also kills their scripts. Defensible,
   but untested and undocumented as a consequence.

## 8. Documentation

`MIGRATING.md` and `API-AUTH.org` are thorough and current. Two corrections needed:

- **`SECURITY.md`'s line-count claim is now false.** Update it, and split it honestly:
  ~5,900 lines of server plus adapters, ~180 browser, ~1,000 optional client that a server
  operator never installs. The framing "a reviewer can read the whole authentication path"
  survives if the optional package is excluded from the number; it does not survive quoting
  3,500.
- The five docs under `docs/API-AUTH/` are design history, including two superseded
  treatments and a `PROVISIONING.md` that `API-AUTH.org` says it supersedes. Fold them into
  one design note, or mark them `docs/API-AUTH/history/`, before a reader mistakes a
  superseded proposal for the design.

## Prioritized actions

**Do before merge**

1. Export the new types from `index.ts`. Hard defect.
2. Table-driven rejection tests for `dpop.ts`. Highest correctness value on the branch.
3. Fix the `SECURITY.md` line-count claim.
4. Ed25519: test it in both packages, or stop exporting `EDDSA`.

**Do before release**

5. Cut per-kind `sessionIdleMs`; keep `sessionAbsoluteMs`. Removes the hot-path second
   check, the clamping rule and a whole divergence class.
6. Replace the `localwebauthn_dpop` regex with per-migration `newTables`.
7. Collapse `issueEnrollment`'s union into an options object.
8. Add `dpopChallenge()` to `http.ts`.
9. One test that the scoped and unscoped revokes agree for a single-kind user.

**Consider**

10. Split the DPoP store methods into a separate optional contract.
11. Reorganize `docs/API-AUTH/` so superseded designs are visibly superseded.
12. Decide and document whether `revokeCredentialTree` should respect `kind`.

## Is the complexity appropriate?

For `kind`, heritage, the migration machinery and the client package: yes. Each solves a
problem that was demonstrated rather than imagined — issue #11's mislabelled row, the
self-replication hole, the grant-path class upgrade, the un-remediable stolen-session
enrollment. Three of those four were found by probing rather than by reasoning, which is
some evidence the concerns were real.

For per-kind session durations: no. It is the one feature that put complexity on the hot
path in exchange for something a host can already achieve by choosing a smaller number.

The honest summary is that the branch is about 60 lines too clever and about 40 lines
under-tested, and both are in identifiable places.
