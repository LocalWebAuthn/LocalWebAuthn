# Review: machine API credentials and credential kinds

Reviews `feature/machine-api-credentials` against `main` at `35a40c0`. Written at
`1a5e548`; the four **before merge** items, all five **before release** items and two of the
three **consider** items have since been done, and this document is updated as-built. Only
item 11 (reorganizing `docs/API-AUTH/`) remains.

The feature works and is well tested at the seams. The complexity is mostly warranted and
mostly opt-in. But the branch spent its budget unevenly: three of the eight categories
below carried complexity that bought little, one documented promise was false, and the
newest security-critical module was the least tested code in the repository. All three are
now addressed — the reading surface is the same size, but the hot path, the configuration
rules and the divergence-prone spots are simpler, and the untested parts are tested.

`SECURITY.md` claimed "about 3,500 lines of TypeScript … so that a reviewer can read the
whole authentication path rather than trust it." It was 7,131 at review time. **That claim was
load-bearing for the project's pitch and the branch silently broke it.** ✅ Corrected: it
now gives the real figure split by package, with a note that a deployment not issuing API
credentials can skip `dpop.ts` and the `credentialKinds` handling.

The before-release simplifications did not shrink that number — they added 28 lines net.
Cutting per-kind `sessionIdleMs` removed about 20; `dpopChallenge()` and the per-migration
`newTables` machinery added more back. What they bought was fewer _rules_: one liveness
check instead of two, one revoke cutoff instead of two, no clamping special case, no table
name inside a regex. Lines are the wrong unit for that, but they are the unit `SECURITY.md`
promises, so the honest statement is that the audit surface is unchanged while the reasoning
surface is smaller.

Two costs are being conflated and should be separated. The _default-path behaviour_ barely
moved: a host that declares no `credentialKinds`, configures no `dpopNonce` and never sets
a `credentialKind` now sees exactly one change, the kind-scoped last-credential guard —
cutting per-kind `sessionIdleMs` removed the other one, the widest-idle window in
`revokeUserSessions`. The _reading surface_ grew 73%. The first cost is genuinely near zero;
the second is real and unavoidable for anyone auditing.

## 1. Schema and migrations

Collapsing four development versions into one was right and the migration test — building
from the literal released v1 DDL out of git history, then asserting structural equivalence
with a fresh install — is the strongest correctness artifact on the branch.

One fragile spot, now fixed. It was:

```ts
const newTables = schema.filter((statement) =>
  /^CREATE (TABLE|INDEX|UNIQUE INDEX) IF NOT EXISTS localwebauthn_dpop/u.test(statement),
);
```

A table name hard-coded into a filter. The next schema change that added a table would
silently not create it on upgrade, and only a fresh install would work — the same failure
shape as the `applied_at INTEGER` overflow, which also only appeared on a fresh database.

✅ Each version now declares what it introduces, next to the ALTERs where a reader is
already looking:

```ts
{ version: 2, statements: [...], newTables: ['localwebauthn_dpop_proofs', 'localwebauthn_dpop_nonces'] }
```

`localWebAuthnUpgradeStatements` lifts each named table's `CREATE TABLE IF NOT EXISTS` and
every index defined over it, and **throws** if a named table is absent from the schema — so
a typo fails loudly instead of producing the divergence it was meant to prevent. The
statement list is byte-identical to the regex's in both dialects, which was checked rather
than assumed, and `tests/server/migrations.test.ts` asserts both the lifting and the guard.

Also note the review-visible hazards the schema now carries, both already documented but
both discovered the hard way: no `--` comments (the splitter collapses whitespace and
comments out the following statement), and no new `CHECK` constraints (SQLite cannot ALTER
one in, so fresh and upgraded would diverge).

## 2. The store contract: 16 → 20 required, 3 optional ✅

Seven new methods, each individually justified, but the contract is what a custom store
implementer must satisfy. (The review first said 21 → 28; the real counts are 16 → 23,
counted from the type. The +7 was right, the absolute figures were not.) Three of the seven
existed only to serve an optional feature
(`claimDpopProof`, `claimDpopNonce`, `dpopNonces`) — so a host that will never use DPoP had
to implement them, or stub them wrongly, to typecheck.

✅ **Split.** `LocalWebAuthnStore` keeps the 20 every deployment needs;
`LocalWebAuthnDpopStore` carries the three and is needed only when `verifyDpop` or
`dpopNonce` is called. `#dpopStore()` checks for them at the point of use and throws
`invalid_configuration` (500) **naming the missing ones** — `verifyDpop` checks before any
verification work, so a misconfigured store is reported as such whether or not the proof
would have passed.

All three official adapters declare `implements LocalWebAuthnStore, LocalWebAuthnDpopStore`,
so the compiler still holds them to the signatures, and conformance tests the intersection.
Worth recording what the split cost to prove: after moving the methods, the **only** thing
that failed to typecheck was the conformance fixture. Nothing in the service, the demo, or
the starters referred to them, which is the evidence that the three were separable rather
than merely feeling separable.

A test builds a store that implements the required contract and nothing more — a `Proxy` that
hides two of the three methods — and asserts both entry points refuse it by name while
`issueEnrollment` still works.

`revokeLiveCredentialSessions` and `revokePendingEnrollmentGrants` are both service-layer
loop helpers introduced to avoid variable-length `IN (...)`. That trade was right — dynamic
SQL leaving `queries.ts` would be worse — but it should be said out loud that it costs one
round trip per credential.

## 3. Per-kind session durations — cut ✅

The strongest simplification available, and now done. `credentialKinds[kind].sessionIdleMs`
cost, together with `.sessionAbsoluteMs`:

- `#widestIdleMs` computed in the constructor;
- a **second liveness check in `resolveSession`**, the hottest path in the package, because
  the store must filter on the widest window before the kind is known;
- a config clamping rule with its own error case (`sessionIdleMs` inherited vs explicit),
  which a test had to discover;
- a divergence class: `revokeUserSessions` was computing liveness from the _global_ window
  and would have left a longer-windowed session alive after "sign out everywhere". Found and
  fixed, but it was created by this feature.

What it buys: machine sessions can expire sooner than human ones. But the machine client
re-authenticates on `401` for two round trips, so a host can get the same effect by simply
setting a short global `sessionAbsoluteMs`, or by not caring.

**Done:** `sessionIdleMs` is gone from `CredentialKindPolicy`; `sessionAbsoluteMs` stays and
needs _no_ `resolveSession` change at all, because absolute expiry is stamped on the row at
creation. `#widestIdleMs`, the second liveness check and the clamping rule are deleted, and
both `revokeUserSessions` paths now derive one `idleBefore` from the global window, so the
divergence class is closed structurally rather than by a fix.

The one rule left is stated where it will be read: a kind may shorten its absolute lifetime
below the global idle window, and that is not a misconfiguration, because absolute expiry
wins and the excess is unreachable. `crypto-config.test.ts` pins it.

## 4. Dual-path bulk revokes

`revokeUserSessions` and `revokeUserAuthentication` each have a scoped and an unscoped
implementation reaching different SQL. That structure is what produced the bug where the
scoped `revokeUserAuthentication` left pending grants alive — a live grant of a revoked
kind being standing authorization to re-enroll straight back in.

Two behaviours that are supposed to agree, implemented twice, is the shape that generates
that class of bug. It will generate another.

**Done — the second option.** Both paths remain, because collapsing them would put an extra
query on the unscoped path that every deployment pays for, and `tests/client/round-trip.test.ts`
now asserts they are indistinguishable for a single-kind user: same count, same live
sessions, same active credentials, same grant state, for both `revokeUserSessions` and
`revokeUserAuthentication`. The assertion was confirmed to have teeth by removing the scoped
grant revoke and watching it fail on `grantLive`.

Unconsumed challenges are the one deliberate difference — the unscoped path clears them, the
scoped path leaves them — which is harmless, because a challenge whose credential or grant is
revoked can no longer complete. That is now written down in the test rather than only in
`MIGRATING.md`.

## 5. DPoP verification ✅ done

Was the weakest spot on the branch: **70.2% statements, 64.9% branches**, the lowest of any
module and the newest security-critical verification code. Roughly twelve of fifteen
rejection paths had never been exercised, including `private_key_in_jwk`, which exists
purely as a key-confusion guard, and the entire OKP/Ed25519 branch of `coseToJwk` at zero
hits.

`tests/server/dpop.test.ts` is now table-driven over every reason string, with a case that
starts from a proof which verifies and applies the smallest change that should break it.
Header checks run before signature verification so those cases corrupt the header directly;
payload checks run after it, so those re-sign — otherwise they would fail as `bad_signature`
and prove nothing about the payload rule. A final case reads the module source and asserts
the set of `invalid('…')` reasons equals the set of table keys, so a reason cannot be added
without a test again.

**96.2% statements, 96.3% branches.** The four remaining lines are defensive `catch` and
early-return guards that are unreachable from `verifyDpopProof` because an earlier check
already covers them.

Writing the tests found two real bugs, which is the argument for having written them:

**`coseToJwk` threw instead of returning `null`.** `decodeCredentialPublicKey` is _typed_ as
returning a Map but hands back whatever the CBOR decoded to — a bare integer for
`Uint8Array.of(0)` — and the type guards then called `.get` on it. The `try` only wrapped
the parse, so the `TypeError` escaped. A verifier that throws produces a **500 where a 401
was intended**, and it meant `unsupported_credential_key` was unreachable. The whole decode
is now guarded.

**`malformed_jwk` was dead code.** It sat behind `try { jwkThumbprint(…) } catch`, but
`jwkThumbprint` interpolates its members into a template string and cannot throw on any
value `JSON.parse` can produce. So a jwk missing `y` hashed the literal text `"undefined"`
and failed the comparison _by accident_ — and two differently-malformed jwks could hash
identically (`{}` and `{"kty":"OKP"}` collide). Replaced with an `isPublicJwk` structural
check before hashing, which makes the rejection deliberate, reachable and tested, and stops
it masquerading as `key_mismatch`.

Ed25519 is now covered in both packages: a `verifyDpopProof` case, `coseToJwk`'s OKP branch
including its two validation failures, and a full client-side registration plus assertion
round trip. It works — raw 64-byte signatures rather than DER, OKP COSE rather than EC2 —
so `EDDSA` stays exported. Client `keystore.ts` went 81.0% → 95.2% as a side effect.

## 6. Host ergonomics ✅ done

Three warts, all fixed while the API is unreleased.

**None of the new types were exported.** ✅ Fixed. `index.ts` was untouched, so a host
could not name `CredentialKindPolicy`, `CredentialProvenance`, `RegistrationOptionsInput` or
`AuthenticationOptionsInput` — writing a typed wrapper around `registrationOptions` was
impossible without reaching into `dist/types-*.d.ts`. Those four are now exported, along
with `NormalizedConfig` and `NormalizedCredentialKind` (the type of the public `auth.config`),
`kindPolicy`/`defaultKindPolicy`, and the DPoP primitives `verifyDpopProof`, `coseToJwk`,
`jwkThumbprint` with `PublicJwk`, `DpopVerification` and `DpopVerificationInput`. The last
group was not strictly part of the defect, but exporting it also removed a deep
`packages/server/src/dpop.js` import from the tests, which were reaching past the public
API to reach code a host might reasonably want.

**`issueEnrollment(userId, string | { … })`** took a union so the positional
`approvedByUserId` kept working. ✅ Collapsed to the options object, across 10 sites in 8
files — two in `examples/`, the rest tests — since every other caller passes no second
argument at all.

Correcting the review as written: the positional form **was** released, in 2.2.0 — `main` at
`35a40c0` has `issueEnrollment(userId: string, approvedByUserId?: string)`. So this is a
breaking change for any host that passes an approver, not the free removal of dead
compatibility I described. It is still the right call, because the alternative is a permanent
union a reader has to destructure mentally, and the compiler flags every site; but it belongs
in the release's breaking-changes list, and `MIGRATING.md` now says so.

**The nonce challenge was a four-step protocol in every host:** catch `dpop_nonce_required`,
call `dpopNonce()`, set `DPoP-Nonce`, set `WWW-Authenticate` — four things to get right, per
host, for one RFC behaviour, which is precisely what `authCookieNames` and `cookieAttributes`
exist to prevent. ✅ `dpopChallenge(nonce)` in `http.ts` returns the header pair, and the
demo's `requireMachineSession` passes it straight to `context.json(body, 401, headers)`
instead of naming either header. `verifyDpop` still throws, which keeps one error path for
every DPoP failure rather than making this one case return a value.

### Load-bearing decisions — do not silently undo

Each of these looks like an inconsistency until you know why. Changing one needs a reason
better than tidiness.

1. **Only server-chosen facts are controls.** `origin`, `userVerified`, the flags, the
   counter and the AAGUID are all asserted by whatever produced the assertion, so a software
   client can claim any of them. `kind`, the challenge, revocation state and heritage are
   server rows. Every restriction in this feature rests on that split.
2. **`signCount` is pinned at 0 for software credentials.** Not laziness: a strictly
   increasing counter makes concurrent sessions from one credential fight over a single
   compare-and-swap, and unlimited concurrent sessions is a requirement. It also matches
   Apple passkeys, which report 0 forever.
3. **`canRegister` cannot gate the enrollment-grant path.** That path's authorization is
   possession of a single-use token, with no session to inspect, so the package cannot tell a
   person from a program there. Confinement comes from the grant's own `credential_kind`, and
   from the host refusing non-interactive kinds at its session middleware — see
   `LocalWebAuthn.interactiveKind`.
4. **DPoP nonces are per _deployment_, not per credential or per session.** A nonce is not a
   secret; the server hands the current one to any caller. Its only property is being
   unguessable _in advance_, which clock-slot rotation gives globally.
5. **`parent_credential_id` may be a foreign key only because credentials are never
   deleted.** `grant_id` and `approved_by_user_id` must stay non-FK copies, because grants are
   reaped by `cleanup`.
6. **`COALESCE(x, '')` in the kind-scoped index and guards is required**, not decorative:
   NULLs are distinct in a unique index on both engines, so indexing the bare column silently
   drops the invariant for the default kind.
7. **Machine routes are exempt from the origin check by declaration** (`cookieFreePrefixes`),
   and the exemption is sound only because those routes read no cookie. Requiring `Origin`
   from a script would prove nothing — it is a forbidden request-header for _browsers_ only.

## Is the complexity appropriate?

For `kind`, heritage, the migration machinery and the client package: yes. Each solves a
problem that was demonstrated rather than imagined — issue #11's mislabelled row, the
self-replication hole, the grant-path class upgrade, the un-remediable stolen-session
enrollment. Three of those four were found by probing rather than by reasoning, which is
some evidence the concerns were real.

For per-kind session durations: no. It is the one feature that put complexity on the hot
path in exchange for something a host can already achieve by choosing a smaller number.

The honest summary was that the branch was about 60 lines too clever and about 40 lines
under-tested, and both were in identifiable places. Both halves are now addressed.

The under-tested half repaid the effort immediately: writing rejection tests for one
320-line module turned up a verifier that threw a 500 where it meant to refuse with a 401,
and a guard that had never been able to fire. Neither would have been found by reading it —
I had read it, several times, and written the reasoning it was implementing.

The too-clever half repaid it differently. Cutting per-kind `sessionIdleMs` and the
table-name regex removed no bug that existed; both changes removed the _shape_ that had
already produced one bug each — a `revokeUserSessions` computing liveness from the wrong
window, and an `applied_at INTEGER` that only a fresh database revealed. That is the weaker
kind of evidence, and worth saying plainly: these two changes are bets that the same shapes
would have failed again, not fixes for observed failures. The revoke agreement test is the
opposite — it was verified to fail against a reintroduced divergence, so it earns its place
by demonstration.

What remains is item 11, moving the superseded designs under `docs/API-AUTH/history/`, which
touches no code. Items 10 and 12 are done: the store contract now asks a host for only what
its deployment uses, and `revokeCredentialTree` can be scoped by kind while still defaulting
to the blast radius a compromise actually has.
