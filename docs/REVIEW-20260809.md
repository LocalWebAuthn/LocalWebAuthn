# Security and release review: CLI passkeys

Reviews feature/machine-api-credentials at 582ab79 against the production main branch and
release v2.2.0. This is a prospective remediation handoff for the proposed v3.0.0 release.
Unlike earlier review documents that record completed work, the findings below are open
unless explicitly marked otherwise.

The review covered all tracked README*.org files, SECURITY.md, the current and historical
documents under docs/, the server, browser and client packages, the demo, all three official
stores, migrations, package metadata, and release automation. Validation was performed
through the development environment supplied by flake.nix.

## Executive verdict

Do not release v3.0.0 yet.

The basic design is good:

- credential kind is server-selected rather than asserted by an untrusted client;
- machine credentials are excluded from human authentication by default;
- canRegister prevents machine credentials from becoming self-replicating authorities;
- DPoP is tied to the same credential key rather than separate mutable session metadata;
- the server stores credential public keys and token digests, not credential private keys;
- MachineKeyStore is the correct abstraction for opaque software, agent, hardware and KMS
  signers.

Four issues are release blockers:

1. The D1 released-v1 to v2 migration path is broken.
2. The release workflow does not validate or publish @localwebauthn/client.
3. Credential-tree and scoped compromise revocation can miss credentials registered
   concurrently with remediation.
4. DPoP protection is a host convention assembled from separate calls, while the
   documentation presents it as an enforced property of machine sessions.

The private-key security claim also needs correction before release. The narrow persistent
server-custody claim is valid. The current repository-wide claim that project code never
possesses private-key material is not: optional client and provisioning code transiently
handles exportable private keys. The preferred design is to generate durable keys on the
target CLI machine and isolate exportable-key compatibility code from the client core.

## 1. Release blocker: D1 migration does not upgrade a v1 database

> **Status — RESOLVED (`66f6eed`).** `migrateD1` is now version-aware (Approach A): it creates
> the migrations table, reads the stored version, and runs `localWebAuthnUpgradeStatements` for
> the gap plus the version stamp in one `batch()`, with a re-read guard so a concurrent loser
> treats a rolled-back duplicate-column batch as success. The dead
> `localWebAuthnMigrationStatements` helper is deleted. `tests/server/migrations.test.ts` builds a
> literal released-v1 D1 through Miniflare and asserts version, structural equivalence with a fresh
> install, v2 columns present, v1 rows preserved (new columns null), idempotency, and a usable
> store; the former failure ("no such column: kind") was reproduced against the old logic before
> the fix. **Correction to this review:** the D1 batch _is_ atomic — Cloudflare documents a failed
> statement as rolling back the whole sequence — so the "orphan credential" hazard the old
> SECURITY.md described does not occur; that section is rewritten. PostgreSQL is already
> version-aware, so its literal-v1 fixture is a nice-to-have, still open.

### Observed implementation

packages/server/src/d1.ts, migrateD1, prepares only the current
localWebAuthnSchemaStatements result followed by insertion of the current schema version.
It does not:

- read SQL.selectSchemaVersion;
- distinguish an empty database from a released v1 database;
- call localWebAuthnUpgradeStatements;
- execute the v1 to v2 ALTER TABLE statements.

CREATE TABLE IF NOT EXISTS does not add columns to an existing v1 table. Later schema
statements create indexes over v2 columns such as credential kind, so an upgrade from v1
fails rather than producing the v2 schema.

packages/server/src/schema.ts also exports localWebAuthnMigrationStatements. Its comment says
ALTER statements are appended for this purpose, but the function presently combines the
full schema and a version stamp and is unused by the D1 runner. It is not a working upgrade
path.

docs/MIGRATING.md and README-DETAIL.org state that migrateD1 reads the current version and
applies missing migrations. That statement is false for the current implementation.

### Correct D1 transaction model

SECURITY.md, README-DETAIL.org, COMPARISON.md and comments in the query layer describe D1
batch execution as non-atomic and reason about a schema version being stamped after a
partial migration. Current Cloudflare D1 documentation says batch statements execute as a
SQL transaction: a failed statement aborts and rolls back the sequence.

Primary reference:
https://developers.cloudflare.com/d1/worker-api/d1-database/

This means the immediate failure mode is clean rollback and application startup failure,
not the documented partial schema or orphan row. It does not make the missing upgrade logic
acceptable.

### Remediation approaches

**Approach A — recommended: version-aware transactional D1 runner**

1. Read the installed version.
2. For an empty database, install the current schema and stamp it.
3. For each missing version, run its upgrade statements and version insertion in one D1
   batch.
4. Make the version insertion a guarded claim so two workers starting concurrently cannot
   both make incompatible decisions.
5. Re-read and validate the final version.

The exact concurrency construction should be tested against D1 semantics. One viable form
is a unique version insert in the same transaction as the corresponding DDL, treating a
lost version claim as a signal to re-read rather than continuing from stale state.

**Approach B: official D1 migrations**

Move D1 schema evolution to Cloudflare migration files and deployment tooling while keeping
the library runner for SQLite and PostgreSQL. This is operationally conventional but gives
D1 deployments a distinct migration mechanism that must be documented and supported.

**Approach C: reconstruct tables**

Create v2 tables, copy v1 data, validate, swap and stamp in one transaction. This is more
work and is warranted only if future D1 ALTER limitations require it.

### Required tests

- Construct a D1 database from the literal DDL released in v2.2.0.
- Insert representative credentials, sessions, grants and challenges.
- Run migrateD1 and assert structural equivalence with a fresh current schema.
- Assert preservation of every v1 row.
- Run the migration twice and assert idempotency.
- Exercise two concurrent migration attempts if the test environment permits it.
- Add equivalent literal-v1 migration fixtures for PostgreSQL; SQLite already has the
  strongest coverage.

## 3. Release blocker: compromise revocation is vulnerable to registration races

> **Status — PRACTICAL RACE CLOSED (`66f6eed`); absolute fence still open.** Chosen: Approach C
> (root-first, fixed-point re-enumeration) through a shared `#revokeCredentialsToFixedPoint`
> helper serving both `revokeCredentialTree` and the scoped `revokeUserAuthentication` — which
> also collapses the "one behaviour, two implementations" structure this review flagged elsewhere.
> This leans on an invariant already present in the store: the conditional insert
> (`insertCredentialIfSessionValid` / `insertCredentialIfGrantValid`) requires the authorizer's
> `revoked_at IS NULL` _inside the registration transaction_, so a registration whose authorizer
> is revoked before it commits fails, and re-enumeration catches any child that committed just
> before its parent was revoked. `tests/client/round-trip.test.ts` drives the exact interleaving
> deterministically (a store proxy commits a fresh child right after the descendant snapshot) and
> proves single-snapshot leaves it active while fixed-point revokes it; confirmed discriminating by
> mutation.
>
> **Deliberately not fully implemented: the registration epoch (Approach A).** Re-enumeration does
> not fence a sustained attacker who wins the registration race in _every_ pass. The complete
> guarantee is a per-user (or per-tree) generation captured on the challenge at
> `registrationOptions` time, verified inside the credential insert, and bumped by revocation — so
> one bump invalidates every in-flight registration at once. That needs a schema column folded into
> the unreleased v2 migration, capture/verify across all three adapters, and a bump in the revoke
> paths; it is the right next step and is scoped but not built here. Until it lands, SECURITY.md and
> README-DETAIL.org state the residual and tell a host to also stop accepting registrations during
> incident response, and the loop is bounded (logged best-effort stop) so it cannot livelock.

### Observed implementation

In packages/server/src/service.ts, the subtree revocation path first enumerates credential
descendants and then revokes credentials and related state one at a time. The scoped
revokeUserAuthentication path similarly enumerates credentials and performs a sequence of
per-credential revocations.

An attacker holding an authorizing session can race the snapshot:

1. Remediation reads the current descendants.
2. The attacker registers a new child credential.
3. Remediation revokes the snapshot.
4. The new child was never in the snapshot and remains active.

The scoped user/kind operation has an even harder version of this problem because a spared
credential kind may remain authorized to create credentials while the selected kind is
being revoked.

This contradicts the descriptions of credential heritage and bulk revocation as complete
compromise-remediation primitives.

### Security requirement

After a successful remediation operation, no credential or pending authorization created
from an authority covered by that operation may remain usable, including one created
concurrently.

### Remediation approaches

**Approach A — recommended: revocation generation or fence**

Add a generation/fence to the relevant authority:

- a user-level authentication generation for whole-account remediation;
- optionally a user-and-kind generation for scoped remediation;
- a credential revocation generation for subtree remediation.

Registration captures the generation used to authorize it. The transaction that inserts the
new credential must verify that the generation is unchanged and that the authorizer remains
active. Remediation increments the generation before or atomically with revocation. A
registration authorized before that increment can no longer commit afterward.

This provides an explicit invariant that can be implemented consistently across adapters.

**Approach B: store-level locked transaction**

Move the complete revoke operation into a store primitive that takes appropriate row or
database locks, enumerates descendants, revokes related sessions/grants and commits
atomically. Registration must acquire a conflicting lock.

This can work well in PostgreSQL and SQLite but may be awkward to express consistently in
D1. It also expands the required custom-store contract.

**Approach C: root-first fixed-point revocation**

For unscoped subtree revocation, revoke the root authority first, then repeatedly enumerate
and revoke descendants until no active descendants remain. Once the authorizer is dead, no
new valid children should be creatable.

This is simpler but must still ensure that registration re-checks the authorizer at commit.
It does not by itself solve scoped revocation while spared authorizers remain.

**Approach D: weaken the promise**

Rename and document the operation as best-effort enumeration and tell hosts to disable
registration during incident response. This avoids a false guarantee but is not a good
default for an authentication library advertising credential heritage as remediation.

### Recommended implementation sequence

1. Write a deterministic race test with barriers around descendant enumeration and
   registration commit.
2. Confirm it produces a surviving credential on the current implementation.
3. Introduce the smallest generation/fence representation that covers subtree and
   user/kind revocation.
4. Enforce the fence in the same transaction as credential insertion.
5. Make bulk revoke and grant/session cleanup store-atomic where each adapter permits it.
6. Retain the race test for SQLite, PostgreSQL and D1.

## 4. Release blocker: DPoP is not an enforced machine-session invariant

> **Status — RESOLVED (`66f6eed`).** Chosen: Approach A. `authenticateMachineRequest({ sessionToken,
proof, method, url, requireNonce })` is one fail-closed operation — it resolves the session from
> the token **without** touching activity, verifies the DPoP proof against that session's credential
> and that exact token, and only then refreshes `lastSeenAt`. Because the session is derived from
> the token there is no separate `session` argument to mismatch. The demo's `requireMachineSession`
> now calls it and returns one generic 401 for every DPoP failure (also closing the §11
> reason-disclosure leak). Tests: valid proof accepted with a returned nonce; a bearer-only request
> refused _and_ leaving idle activity untouched (so the session idles out — mutation-confirmed that
> touching before the proof fails this test); activity refreshed only on a held proof; and a proof
> for one token rejected against another. **Configuration decision:** the phantom `requireDpop`
> credential-kind option is _removed_ from docs rather than implemented — enforcement is structural
> (a machine route calls `authenticateMachineRequest`, which always requires a proof), so a client
> `dpop: false` simply fails closed rather than silently downgrading. `verifyDpop` stays as the
> lower-level primitive with a docstring steering callers to the safe method.

### Observed implementation

A machine login produces an ordinary bearer session token. It is sender-constrained only if
the host independently:

1. extracts the token;
2. resolves the corresponding session;
3. extracts the DPoP proof;
4. calls verifyDpop with the correct token and session pair;
5. handles the nonce challenge;
6. avoids touching the session before proof succeeds.

packages/server/src/service.ts currently accepts sessionToken and session as separate
verifyDpop inputs. Nothing in that API proves they correspond. The demo resolves the session
before DPoP verification, and resolveSession updates activity. A thief holding only the
bearer token cannot pass DPoP, but can keep the idle timeout refreshed until absolute expiry.

docs/API-AUTH.org documents a credential-kind requireDpop setting that does not exist.
README and SECURITY tables say a live machine token is unusable on its own without
qualifying that this is only true on routes whose host integration enforces DPoP correctly.

### Remediation approaches

**Approach A — recommended: one fail-closed authentication method**

Add a service method shaped like:

```text
authenticateRequest({
  sessionToken,
  dpopProof,
  method,
  url
}) -> resolved authenticated session
```

It should:

1. resolve the raw token without touching the session;
2. derive the credential and kind from that exact session;
3. determine from server configuration whether DPoP is mandatory;
4. verify the proof against that exact token, credential key, method and URL;
5. claim nonce and proof identifier atomically;
6. touch the session only after successful authentication;
7. return the authenticated identity and any response nonce metadata.

Hosts should not be able to accidentally pair a token with a different resolved session.

**Approach B: make resolveSession proof-aware**

Extend resolveSession with request authentication data and require proof for kinds configured
as DPoP-required. This produces the strongest default but changes the existing human-session
API and may make framework-neutral integration less convenient.

**Approach C: typed host middleware**

Provide first-party adapters for common Request-style runtimes that exclusively expose a
verified machine-session result. Keep the lower-level methods but mark them advanced and
unsafe to compose without following a documented sequence.

### Configuration decision

Either implement the documented requireDpop policy, or remove it from the documentation.
If implemented, a machine/service credential kind should normally fail configuration unless
DPoP support is available. The current client option dpop: false must not silently downgrade
a server policy.

### Required tests

- A token for session A cannot be paired with the resolved session for B.
- A failed or missing proof does not update last activity.
- A token-only attacker cannot extend idle lifetime.
- DPoP-required kinds cannot use bearer-only protected routes.
- Human kinds continue to work without DPoP under the chosen policy.
- Missing DPoP store methods fail as configuration errors before authentication work.
- All nonce challenges have the exact RFC-required headers.

## 5. Private-key custody, transient possession and component isolation

### Claim that can be made

The server package does not receive or persist credential private keys. Its durable
authentication state consists of credential public material, token digests and metadata.
This remains an important property.

### Claims that cannot be made

SECURITY.md and README.org also say that no private key passes through code in this
repository or that the project never possesses it. Optional shipped code contradicts that
broader wording:

- packages/client/src/keystore.ts generates an extractable WebCrypto private key and exports
  PKCS#8;
- importKeyStore processes caller-supplied private-key material as base64 text, buffers and
  CryptoKey objects;
- examples/demo/src/client.ts builds a complete credential in browser state and displays it
  for clipboard or download;
- the material can exist simultaneously in a CryptoKey, ArrayBuffer, base64 string, UI
  state, DOM, clipboard, download and operator-created backup.

docs/API-AUTH.org says the provisioning page destroys the key and that exactly one private
copy exists. JavaScript and WebCrypto cannot establish either statement. The WebCrypto
specification does not require implementations to zeroize key material when application
references disappear.

Primary reference:
https://www.w3.org/TR/WebCryptoAPI/

### Recommended wording

Use a component-specific claim:

> @localwebauthn/server never receives or persistently stores credential private keys; it
> stores public credential material and one-way token digests. Browser-mediated human
> passkeys remain under their authenticator or provider. Optional software-key and
> provisioning components may transiently process exportable private-key material, and
> operator-selected keystores may persist it outside LocalWebAuthn server state.

Also distinguish three properties throughout the documentation:

- server persistent custody;
- transient process possession;
- exportability and persistence in the selected client keystore.

### Preferred architecture: target-side key generation

The durable key should be created on the machine that will use it:

1. A recently authenticated human calls issueEnrollment with credentialKind service and
   records the approving user.
2. The UI displays or transfers a short-lived, single-use enrollment capability, not a
   durable private key.
3. The CLI generates the key through MachineKeyStore.
4. The CLI obtains registration options, constructs the software WebAuthn response and
   completes verification.
5. The CLI proves possession before the credential becomes active.
6. Only the public credential key reaches the server.

Add a high-level enroll operation to @localwebauthn/client so hosts do not need to reproduce
the ceremony.

The enrollment capability is still a bearer secret and must be short-lived, single-use,
scope-bound, redacted from logs, and rejected after the approving human session is revoked.
It is nevertheless much safer to transfer than a durable private key.

### Stronger future UX: device authorization

Use an RFC 8628-shaped flow:

1. CLI generates the key and creates a pending request containing the public key, label and
   a high-entropy polling secret.
2. CLI displays a verification URI and short human code.
3. A human authenticates with a fresh passkey in a separate browser.
4. The approval page displays the exact label and public-key thumbprint.
5. CLI proves key possession and polls for approval.
6. Server atomically activates the credential; pending requests expire and are rate-limited.

RFC 8628 is a pattern rather than a directly reusable LocalWebAuthn protocol:
https://www.rfc-editor.org/rfc/rfc8628.html

### Package isolation

Keep MachineKeyStore in a client core that exposes only public-key discovery and signing.
Move raw private-key operations behind explicit entry points:

- @localwebauthn/client/core — proof construction, enrollment and opaque signer interfaces;
- @localwebauthn/client/platform-* — OS, TPM, Secure Enclave, agent or KMS-backed signers;
- @localwebauthn/client/unsafe-exportable or file-key — PKCS#8 generation/import and
  environment-file formatting;
- demo-only provisioning code outside normal production exports.

Add dependency-boundary checks so server and browser packages cannot import the exportable
key module. Name the unsafe boundary in package documentation and generated declarations.

The most fail-safe deployment is an external signer or hardware-backed implementation. The
main process sends bytes to sign and receives a signature but never receives key bytes. A
compromised main process may still use the signer while authorized, but it cannot exfiltrate
the durable key.

### If browser minting remains

Treat it as an explicitly unsafe/exportable compatibility path:

- serve a minimal audited bundle from a dedicated origin;
- load no third-party JavaScript and register no service worker;
- use a strict CSP, frame-ancestors none, Cache-Control no-store, a restrictive referrer
  policy, a restrictive permissions policy and Trusted Types where supported;
- do not copy to clipboard or download by default;
- warn that clipboard history, Downloads, backups, extensions and crash dumps can retain
  copies;
- make the server-side credential pending until the destination proves possession;
- expire/revoke unactivated credentials and any session created during registration;
- clear mutable buffers in finally blocks as best effort, never as a zeroization guarantee.

### Low-level improvements

- Prefer Uint8Array input over immutable base64 strings at raw-key boundaries.
- Minimize decoding and import copies and fill mutable buffers in finally.
- Avoid importing the private key as extractable merely to derive its public JWK. Either
  parse the public point from PKCS#8/SPKI metadata, or store a public JWK alongside the
  private material and verify that it matches.
- Keep the signing CryptoKey non-extractable after import.
- Make file-backed persistence an adapter owned by the application, with explicit file
  permissions and atomic-write guidance.

### Required tests

- Core client tests must run without importing any raw private-key module.
- Package export tests must prove unsafe operations are absent from the default entry point.
- Target-side enrollment must prove possession before activation.
- Expired, reused and revoked enrollment capabilities must fail.
- A mismatched supplied public JWK and private key must fail.
- Browser provisioning, if retained, must leave an abandoned credential inactive.

## 6. MachineClient retries unsafe requests too broadly

### Observed implementation

packages/client/src/machine-client.ts retries a request once after any 401 carrying a
DPoP-Nonce header. It does not require the RFC 9449 challenge:

WWW-Authenticate: DPoP error="use_dpop_nonce"

The demo adds DPoP-Nonce to successful middleware results before downstream application
handling, so an application-generated 401 can carry a nonce and be replayed automatically.
For POST, PATCH or other non-idempotent requests this can execute an operation twice.
ReadableStream bodies may not be replayable at all.

Primary reference:
https://www.rfc-editor.org/rfc/rfc9449.html

### Remediation

- Retry only when status is 401, DPoP-Nonce is present, and WWW-Authenticate contains the
  precise DPoP use_dpop_nonce challenge.
- Generate a unique proof for the retry.
- Retry safe/idempotent methods by default.
- Require explicit caller opt-in or an idempotency key for non-idempotent methods.
- Reject or require a body factory for non-replayable bodies.
- Separate nonce retry from full reauthentication retry; a general 401 must not implicitly
  replay an application operation.

### Required tests

- Ordinary application 401 with an incidental nonce is not retried.
- Exact nonce challenge is retried once with a new proof identifier.
- POST is not retried without explicit replay safety.
- Stream bodies fail clearly instead of sending an empty or consumed body.
- Repeated nonce challenges stop after the configured bound.

## 7. DPoP request-binding claims are too broad

RFC 9449 binds the access token, HTTP method and normalized target URI. The htu value excludes
query and fragment components, and DPoP does not directly provide HTTP message-body
integrity.

Current threat tables describe htm, htu and ath as binding a captured proof to exactly one
request. Two requests with the same method, origin and path but different query parameters
or bodies share those bound components. The jti replay claim stops later reuse but does not
turn DPoP into an HTTP message signature; a captured proof can still be raced before its
identifier is claimed.

### Remediation

- Describe DPoP as sender-constraining the bearer token, not signing the complete request.
- State explicitly that TLS remains required.
- Do not put authorization-significant distinctions only in an ignored query component.
- Use idempotency keys and normal authorization for mutating operations.
- If exact body integrity is required, add an application content digest or use an
  appropriate HTTP Message Signatures profile:
  https://www.rfc-editor.org/rfc/rfc9421.html

Add tests for URL normalization, ignored fragments, query handling and same-path requests
with different bodies so the documented boundary is deliberate.

## 8. Runtime secret and database-compromise claims need narrower wording

The database-compromise property is strong: stored digests cannot directly authenticate as
the corresponding raw session, challenge or enrollment token.

The broader claim that server logs, traces or crash dumps contain nothing usable is false as
a package invariant. Raw bearer values are generated or received by the server process and
returned through HTTP integration. Instrumentation or a crash dump taken during a request
can capture:

- session tokens;
- enrollment tokens;
- WebAuthn challenges while live;
- Authorization and Cookie headers;
- provisioning responses or URL fragments handled by the host.

Machine credential files are durable until rotation or revocation, not merely time-boxed.

### Remediation

- Say that LocalWebAuthn does not intentionally persist or log raw bearer tokens.
- Distinguish database-at-rest compromise from live-process and observability compromise.
- Provide a host redaction checklist covering Authorization, Cookie, Set-Cookie, enrollment
  values, URL fragments and authentication response bodies.
- Recommend disabling or encrypting production crash dumps and restricting tracing payloads.
- Say that database contents are non-authenticating, not that they contain nothing
  sensitive; they still contain identifiers, public keys, timestamps and relationship
  metadata.

Tests can assert that package-generated error objects and normal logs do not include raw
tokens, but host logging behavior remains an integration responsibility.

## 9. Current API-AUTH documentation is not an implemented reference

docs/API-AUTH.org is presented as the current design but mixes implemented behavior,
superseded design and future proposals. Its generated api-auth.txt and PDF repeat the same
problems.

Known contradictions include:

- claiming all three migration runners perform version-aware upgrades;
- documenting a requireDpop credential-kind option that does not exist;
- showing an older two-member MachineKeyStore instead of the four-method interface;
- showing a DPoP nonce as a login-verification result rather than a protected-resource
  challenge;
- saying the proof cache is the only new table when a nonce table also exists;
- presenting client-version request headers as implemented;
- listing already implemented work as open while referring to schema version 1;
- describing a CLI keychain-binding and shredding flow that does not exist.

### Remediation

Choose one of:

**Approach A — recommended: implementation reference**

Make API-AUTH.org describe only public behavior present in the v3 code. Move future work into
an explicitly non-normative roadmap or historical design document.

**Approach B: status annotations**

Keep the combined document but label every section Implemented, Proposed, Superseded or
Demo-only. This retains rationale but is easier to let drift.

Then:

1. Check every named option and method against exported TypeScript declarations.
2. Check diagrams against the actual demo request sequence.
3. Check schema/table statements against schema.ts.
4. Move important caveats from superseded history documents into the current security
   reference.
5. Regenerate text and PDF only after the Org source is corrected.
6. Add a documentation verification checklist to docs/RELEASING.md.

## 10. Authenticator and Secure Enclave claims are overgeneralized

Documentation contrasts machine credentials with human passkeys by calling the latter
Secure Enclave-backed and never exportable. WebAuthn allows hardware, software, platform,
roaming and server-side/synced authenticators. Backup-eligible credentials can be synced,
imported or recovered depending on the provider. Apple passkeys synchronize through
end-to-end encrypted iCloud Keychain and support account recovery.

Primary references:

- https://www.w3.org/TR/webauthn-3/
- https://support.apple.com/en-euro/guide/security/sec1c89c6f3b/web
- https://support.apple.com/en-ie/102195

### Remediation

- Say that human credentials are mediated by a WebAuthn authenticator.
- Make hardware protection, local-only storage and backup eligibility deployment-specific
  properties, not universal ones.
- If policy depends on attestation, backup eligibility or backup state, document exactly
  what is checked and what trust is placed in that signal.
- Keep the useful semantic distinction: human credentials require authenticator-mediated
  user verification/presence according to policy, while CLI software keys may be unattended
  and exportable.

## 11. Demo failure disclosure and discarded session

### Detailed DPoP errors

examples/demo/src/machine.ts sends caught error.message values to clients. This can disclose
internal DPoP distinctions such as replayed proof, bad signature or key mismatch even though
the verifier comments say those reasons should not be surfaced.

Return one generic authentication failure body. Send structured reason codes only to a
controlled security log with no tokens, proofs or private material.

### Registration-created session

verifyRegistration creates a service session as part of the normal service result. The demo
uses the credential but discards the raw session token without revoking its database row.
That leaves a live but unreachable session until expiry.

Available remedies:

- immediately revoke the returned registration session in the demo; or
- add a registration option that creates the credential without an initial session when the
  caller intends to authenticate separately; or
- use the returned session as the first machine session instead of discarding it.

The first is the smallest demo fix. The second is a cleaner public API if this pattern is
expected to be common.

Tests should assert that provisioning does not increase the count of live unreachable
sessions.

## 12. Credential-file and endpoint validation

packages/client/src/credential-file.ts formats shell-style environment content but does not
quote the keystore value. The current base64 software-key representation is shell-safe, but
MachineKeyStore also advertises arbitrary keystore URIs. A URI containing whitespace,
quotes, shell metacharacters or command syntax is not safe to source.

Credential parsing mostly checks for nonempty strings. It should validate:

- HTTPS base URL except an explicit loopback-development allowance;
- base URL origin and RP ID relationship;
- expected base64url encoding and byte lengths for credential/user handles;
- supported key-store URI scheme;
- absence of control characters and ambiguous duplicate fields;
- a bounded file size.

### Remediation approaches

- Prefer JSON with restrictive file permissions over a sourceable shell file.
- If environment output remains, implement and test POSIX-safe single-quote escaping for
  every value and do not imply that arbitrary URI schemes are safe.
- Parse the credential into a typed validated object before MachineClient construction.
- Enforce HTTPS in MachineClient itself, with a deliberate loopback exception for the demo.

Add adversarial tests using spaces, quotes, dollar signs, command substitutions, newlines,
invalid base64url, Unicode hostnames, userinfo URLs and non-HTTPS remote endpoints.

## 13. Comparison, migration and release documentation drift

docs/COMPARISON.md contains stale package versions, approximate line counts, roadmap
language and broad third-party security claims without durable primary citations. It still
describes the project as young 2.x while this branch is intended as v3, and some roadmap

### Remediation

- Cite primary product documentation for externally verifiable claims.
- Separate factual feature comparison from opinionated design rationale.
- Remove volatile source-line counts or generate them during release.

that passed approvedByUserId positionally in v2.2.0 must move it into the new options object.

## 14. Properties to preserve while fixing the blockers

Remediation should not accidentally weaken these existing invariants:

- Credential kind is chosen from server-held enrollment/grant state, never from a claimed
  registration response field.
- Authentication challenge allowed kinds are fixed before proof verification.
- Noninteractive kinds are excluded when no explicit allowed kind is requested.
- Machine credentials with canRegister false cannot mint their own descendants through a
  live session.
- Human-only routes test server-derived kind rather than client labels.
- DPoP rejects private JWK members, disallowed algorithms, malformed keys, bad signatures,
  stale proofs, method/URI/token mismatches, missing nonce and reused proof identifiers.
- Proof identifiers and nonces are claimed atomically in the store.
- The server retains only public credential material and digests in durable state.
- Official adapters remain subject to one conformance suite.
- MachineKeyStore continues to expose signing behavior rather than requiring callers to
  retrieve raw private bytes.

## 15. Suggested implementation order

The items interact, so resolve them in this order:

1. **Freeze claims:** edit SECURITY.md and top-level README language so current users are not
   relying on guarantees the implementation does not provide.
2. **Repair migration:** implement D1 v1 upgrade and released-schema fixtures before making
   further schema changes.
3. **Design revocation fence:** choose the schema/transaction model before finalizing schema
   version 2. If new columns or tables are needed, incorporate them into the same unreleased
   migration rather than immediately creating v3 schema.
4. **Centralize DPoP authentication:** establish the server invariant, then simplify the
   demo and MachineClient around it.
5. **Move key generation:** implement CLI-owned enrollment and isolate exportable-key
   adapters. If this is deferred, explicitly ship browser minting as a compatibility path
   with the mitigations in section 5.
6. **Fix retries and validation:** tighten nonce retry, credential parsing, URL checks and
   demo failure handling.
7. **Reconcile documentation:** update API-AUTH.org and every security comparison from the
   final implementation, then regenerate derived documents.
8. **Finish release mechanics:** version all packages, add the client license and publish
   path, update changelog/migration notes, and run the complete clean-room release check.

Each completed item should be recorded in this document with:

- the resolving commit;
- the chosen approach and rejected alternatives;
- the tests that demonstrate the former failure and the new invariant;
- any guarantee deliberately weakened instead of implemented.

## 17. Definition of release-ready

This review can be considered resolved when:

- every release-blocker invariant is enforced in code rather than host prose;
- literal v2.2.0 databases upgrade successfully on SQLite, PostgreSQL and D1;
- deterministic race tests prove remediation cannot leave a concurrently derived
  credential active;
- machine-session protected routes cannot resolve or touch without satisfying configured
  DPoP policy;
- default client imports do not expose raw private-key operations, or the release explicitly
  accepts and documents that boundary;
- every normative security claim names the component and threat boundary to which it
  applies;
- all three npm artifacts are complete, version-aligned and publishable;
- the complete Nix-based quality gate and clean-consumer package tests pass from a clean
  checkout.
