Companion to [[./README.org][README.org]], which builds one application up from nothing.
This document is the reference: every option, in the order a deployment meets it.  Nothing
here is required reading to ship the six routes --- but each section is something you will
eventually want an answer for.

For the examples, see
[[./README-DETAIL-EXAMPLES.org][README-DETAIL-EXAMPLES.org]].  For machine credentials in
full, [[./docs/API-AUTH.org][docs/API-AUTH.org]].

* Who owns what

LocalWebAuthn supplies the lifecycle rules and persistence that ceremony libraries leave to
each application, and nothing above them:

| Concern                                        | Owner          |
|------------------------------------------------+----------------|
| Application users, roles, authorization        | Host           |
| Link approval, delivery, identity proofing     | Host           |
| Cookies, exact-origin checks, rate limits      | Host           |
| Enrollment grants and atomic replay protection | LocalWebAuthn  |
| Registration and authentication challenges     | LocalWebAuthn  |
| Credential metadata, counters, revocation      | LocalWebAuthn  |
| Session expiry, touch, logout, revocation      | LocalWebAuthn  |
| SQLite, PostgreSQL and D1 schemas              | LocalWebAuthn  |
| WebAuthn option generation and verification    | SimpleWebAuthn |

The split is deliberate: authentication lifecycle is reusable, while identity proofing and
business authorization are application policy.  [[./docs/RATIONALE.md][docs/RATIONALE.md]]
argues it at length, including the non-goals.

"Self-hosted" describes the relying-party application and its authentication data.  It does
*not* mean zero dependencies: ceremony verification uses =@simplewebauthn/*= as library code
in your process, HTTPS may be terminated by a proxy or CDN (that is transport, not identity),
and a user may sync passkeys through their OS or password manager --- which is not an
identity provider for your application, because it never gives LocalWebAuthn a private key.

* Storage adapters

All three adapters pass one conformance suite, and every =migrate*= call is idempotent, so
calling it on each start is fine.

** SQLite (better-sqlite3)

#+begin_src ts
import Database from 'better-sqlite3';
import { migrateSqlite, SqliteLocalWebAuthnStore } from '@localwebauthn/server/sqlite';

const database = new Database('application.db');
migrateSqlite(database);
// store: new SqliteLocalWebAuthnStore(database)
#+end_src

Real transactions.  The adapter enables =PRAGMA foreign_keys = ON= on the connection it is
given --- in both =migrateSqlite= and the constructor --- so keep using that same connection,
or the schema's foreign keys stop being enforced.

** PostgreSQL

#+begin_src ts
import { Pool } from 'pg';
import { migratePostgres, PostgresLocalWebAuthnStore } from '@localwebauthn/server/postgres';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
await migratePostgres(pool);
// store: new PostgresLocalWebAuthnStore(pool)
#+end_src

Pass a =Pool=, not a single client: transactions need a connection to themselves.  The revoke
path takes =SELECT ... FOR UPDATE ORDER BY id= on the user's credentials, because under
READ COMMITTED a conditional =UPDATE= alone let two concurrent revokes each believe another
credential remained --- which once left an account with zero.

** Cloudflare D1

#+begin_src ts
import { D1LocalWebAuthnStore, migrateD1 } from '@localwebauthn/server/d1';

await migrateD1(env.DB);
// store: new D1LocalWebAuthnStore(env.DB)
#+end_src

D1 runs each multi-statement operation as one =batch()=, which D1 executes as a single
transaction --- a failing statement rolls the whole sequence back
([[https://developers.cloudflare.com/d1/worker-api/d1-database/][Cloudflare D1 Worker API]]).
So a registration commits the credential, grant completion and initial session together or
not at all, the same all-or-nothing the transactional adapters give.  =migrateD1= is
version-aware like the others: it reads the stored schema version and applies only the
missing upgrades, in one batch.  See [[./SECURITY.md][SECURITY.md]] D1 Batch Transactions.

** Maintenance

#+begin_src ts
setInterval(() => void auth.cleanup(), 5 * 60_000);
#+end_src

=cleanup()= reaps expired enrollment grants, finished challenges, dead sessions and spent
DPoP records, and returns the counts.  *It never touches credentials* --- those are durable
authenticators, removed only by revocation.  (Releases 1.0.0 and 1.1.0 did delete idle
credentials here; that is the bug that forced 2.0.0.)

* The six routes

=@localwebauthn/browser= speaks a small JSON protocol over six paths that you implement:

| Route (default)                      | Service call                  | Cookie                                      |
|--------------------------------------+-------------------------------+---------------------------------------------|
| =POST /api/auth/enrollment/exchange= | =exchangeEnrollment(token)=   | sets enrollment                             |
| =POST /api/auth/register/options=    | =registrationOptions({...})=  | sets challenge                              |
| =POST /api/auth/register/verify=     | =verifyRegistration({...})=   | clears challenge + enrollment, sets session |
| =POST /api/auth/login/options=       | =authenticationOptions()=     | sets challenge                              |
| =POST /api/auth/login/verify=        | =verifyAuthentication({...})= | clears challenge, sets session              |
| =POST /api/auth/logout=              | =revokeSession(token)=        | clears session                              |

Change the prefix with =new LocalWebAuthnBrowser({ basePath: '/auth' })=, or any single path
with the =endpoints= option.  Three cookies are involved, all opaque, all hashed before
storage, none readable by JavaScript:

- *challenge* --- lives only between an =options= call and its =verify=.
- *enrollment* --- from link exchange until the first passkey exists.
- *session* --- the actual login.

[[./examples/starter-hono/src/auth-routes.ts][examples/starter-hono/src/auth-routes.ts]] is a
copyable implementation of all six.

* Cookies, origins and CSRF

Use the helpers rather than re-deriving flags; they are the same rules
[[./SECURITY.md][SECURITY.md]] requires:

#+begin_src ts
import {
  authCookieNames,      // __Host- prefixed on HTTPS, plain on loopback
  cookieAttributes,     // HttpOnly, Path=/, SameSite=Strict, Secure, maxAge from expiresAt
  isExactOrigin,        // scheme+host+port equality, no suffix matching
  isHttpsPublicOrigin,
  parseCookieHeader,    // for plain Node/undici adapters
  serializeCookie,
  serializeClearedCookie,
} from '@localwebauthn/server';
#+end_src

=authCookieNames= and =cookieAttributes= *throw* for a plain-HTTP =publicOrigin= that is not
loopback.  WebAuthn will not run there anyway, so issuing non-=Secure= cookies would only
hide the misconfiguration.

Your route layer still owns CSRF and rate limits.  The pattern is one middleware, mounted
before your own routes:

#+begin_src ts
app.use('/api/*', async (c, next) => {
  c.header('Cache-Control', 'no-store');
  if (c.req.method !== 'GET' && !isExactOrigin(c.req.header('Origin'), publicOrigin)) {
    return c.json({ error: 'invalid_origin' }, 403);
  }
  await next();
});
#+end_src

*A route that reads no cookie needs no origin check.*  CSRF requires ambient credentials the
browser attaches by itself; a script sends its token in an =Authorization= header and no
=Origin= at all, so demanding one would prove nothing --- =Origin= is a forbidden request
header that only browsers are obliged to set.  Machine routes are therefore exempted *by
declaration* (the demo calls that list =cookieFreePrefixes=), not by mount order, and the
exemption is sound only because those routes read no cookie.

* Users and suspension

=getUser= is the only place your user table is read.  Return =active: false= to suspend
someone: every ceremony --- issuing and exchanging enrollment links, registration,
authentication --- and every session resolution refuses them immediately, without revoking
anything.  Flip it back and their passkeys work again.

When suspending, decide how far to go:

| Also call                          | Effect                                                      |
|------------------------------------+-------------------------------------------------------------|
| nothing                            | sessions exist but resolve to nothing; fully reversible     |
| =revokeUserSessions(userId)=       | session records ended; passkeys intact                      |
| =revokeUserAuthentication(userId)= | passkeys and pending grants gone; the person must re-enroll |

=webAuthnUserHandle= must be a stable, random 32 bytes --- =createUserHandle()= produces one.
It is what the authenticator stores to name the account, so it must not be an email or an
incrementing id, and it must never change for a user who has credentials.

* Sessions

Defaults, all overridable through =durations=:

| Option                | Default    | Meaning                                       |
|-----------------------+------------+-----------------------------------------------|
| =enrollmentGrantMs=   | 30 minutes | how long an enrollment link may be redeemed   |
| =enrollmentSessionMs= | 10 minutes | from exchange to the passkey existing         |
| =challengeMs=         | 5 minutes  | between an =options= call and its =verify=    |
| =sessionIdleMs=       | 30 minutes | inactivity before a session dies              |
| =sessionAbsoluteMs=   | 8 hours    | total session lifetime regardless of activity |

=resolveSession(token)= applies both windows and touches =lastSeenAt=; pass =false= as the
second argument to inspect a session without extending it.  It returns =null= --- never
throws --- for expired, idle, revoked, revoked-credential and suspended-user cases, so one
check covers all five.

A declared credential kind may shorten =sessionAbsoluteMs= for itself (see
[[#credential-kinds][Credential kinds]]).  The idle window is global on purpose: a per-kind
idle window forces the session lookup to filter on the widest window any kind allows and
then re-check per kind, which is cost on the hottest path in the package for something a host
can get by choosing a smaller absolute lifetime.

* Revocation

| Call                                                              | Ends                                               |
|-------------------------------------------------------------------+----------------------------------------------------|
| =revokeSession(token)=                                            | one session                                        |
| =revokeUserSessions(userId, { exceptSessionToken })=              | every session, optionally sparing the caller's     |
| =revokeUserSessions(userId, { kinds })=                           | only sessions opened by credentials of those kinds |
| =revokeCredential(userId, credentialId, { allowLastCredential })= | one credential and its sessions                    |
| =revokeCredentialTree(userId, credentialId, { kinds })=           | a credential and everything it enrolled            |
| =revokeUserAuthentication(userId, { kinds })=                     | credentials, sessions, and pending grants          |

Two behaviours to know:

*The last-credential guard is scoped by kind.*  =revokeCredential= refuses to remove a
person's only credential *of that kind* unless =allowLastCredential: true=.  Without the
scoping, someone holding one passkey and one API credential could have their only passkey
revoked and be told it worked.

*=revokeCredentialTree= is the remediation primitive.*  A stolen session can enroll a passkey
of its own --- that is the intended "add a passkey" feature for a person, so it cannot simply
be forbidden --- and afterwards the attacker's credential is indistinguishable from a
legitimate one.  Revoking the subtree is the only remedy.  It revokes with
=allowLastCredential= and may empty the account: stopping short would leave a half-revoked
tree, which after a compromise is worse than re-enrolling.

Two mechanisms make it robust against a registration racing it.  It re-enumerates to a fixed
point rather than revoking one snapshot, so a credential that already exists is found on
re-read; and every revoke advances the user's *registration generation*, which every
registration challenge records and the credential insert re-checks --- so a ceremony already in
flight cannot commit behind the revoke.  It fails with =registration_failed= instead.

What the fence does not cover, by design: a credential a =kinds=-scoped revoke *spares* is still
an authorized registrar, so it can obtain a fresh challenge afterwards and enroll again.  That is
authority, not a race.  Treat scoped revocation as administrative, and use the unscoped form for
a compromise --- see [[./SECURITY.md][SECURITY.md]].

Unscoped, it crosses kinds, and that is usually a surprise worth knowing: every API
credential a person provisions has *their passkey* as its parent, so revoking a suspected
passkey's tree stops their scripts too.  After a compromise that is right.  When it is not
what you meant, pass =kinds= --- which restricts what is revoked, not what is walked, so
sparing a credential does not silently spare what that credential enrolled.

* Designing recovery

A user will lose their phone.  What you do next is the most important security decision in a
passkey deployment, and the one this package refuses to make for you.

** Why the bar has to be high

*Account security is the weaker of the passkey and the recovery path.*  A passkey is
origin-bound, unphishable and useless to whoever steals your database.  An attacker looking
at that will not attack it --- they will contact your support address and say they got a new
phone.  Every hour of phishing resistance is refunded the moment recovery is easier than the
front door.  Well-defended accounts are overwhelmingly lost to help-desk social engineering
and SIM swaps, not to broken cryptography.

*Recovery must be at least as strong as enrollment.*  If a new employee gets their link only
after a manager confirms them in person, then recovery that needs a matching email address is
not recovery --- it is a bypass of onboarding, available to anyone who can read that mailbox.

*Recovery is rare, so it may be slow.*  Sign-in happens constantly and must be frictionless.
Recovery happens perhaps once per user every few years.  That asymmetry is a gift: you can
afford a human in the loop, a callback, a 24-hour delay, a video call.  Almost nowhere else
can you buy that much security for that little aggregate friction.  Do not reflexively
automate it.

*The enrollment link is a bearer capability.*  Whoever opens it first gets a working passkey.
Identity-proofing the requester is half the job; the delivery channel is the other half.  A
perfect identity check followed by an email to an attacker's inbox is an account takeover.

** Pattern: administrator-initiated

Best whenever a human can vouch for the person.  The strongest version ships *no self-service
recovery endpoint at all*.

1. The user contacts an administrator out of band.
2. The administrator confirms them through a channel that proves *personhood*, not account
   control: a video call where they recognise the face, an in-person visit, a manager
   vouching.  A caller who knows the employee's manager, start date and desk number has
   proven only that they did some research.
3. Revoke, then issue, then deliver over a channel bound to the person rather than the
   account --- an existing session on a managed device, or hand to hand.

#+begin_src ts
// Order matters. revokeUserAuthentication() revokes pending enrollment grants,
// so issuing first would destroy the link you just made.
await auth.revokeUserAuthentication(user.id);
const { enrollmentUrl } = await auth.issueEnrollment(user.id, {
  approvedByUserId: administrator.id,
});
#+end_src

=approvedByUserId= is stored on the grant and copied onto any credential it creates, so every
recovery has a named person accountable for it.  That record is worth more than it looks: a
recovery nobody signed off on is exactly the shape a social-engineering attack leaves behind.

** Pattern: multiple independent channels

For consumer systems with no administrator, require proof of control over two channels the
user registered *before* the loss --- typically a verified email address and phone number.
Verify both before issuing anything, and send the link only to the address already on file.

Three failure modes to design against:

- *The channels must be genuinely independent.*  If the phone number is the reset method for
  the email account, they are one factor wearing two hats.
- *A phone number is weaker than it feels.*  Numbers get ported and SIM swaps are cheap and
  targeted.  Treat "controls the number today" as one piece of evidence --- awkward precisely
  in the case you are designing for, where the legitimate user genuinely does have a new
  phone and possibly a new SIM.
- *Never let the request choose the destination.*  Address and number come from the user
  record, not the form.

** Whichever pattern you choose

- *Revoke before you issue.*  If the device was stolen rather than lost, this is what evicts
  whoever has it.
- *Shorten the window.*  Drop =durations.enrollmentGrantMs= well below 30 minutes for
  recovery links; they should be used within minutes of a live conversation.
- *Tell the user on every channel you have,* at initiation and completion.  A legitimate user
  who did not ask for this is your best intrusion detector, and a cool-off period gives them
  time to object.
- *Keep the audit trail.*  =onEvent= emits =enrollment.issued=, =enrollment.revoked= and
  =enrollment.completed= with a =grantId= you can join against the grant's
  =approved_by_user_id=.  Persist them; recovery is the flow you will most want to
  reconstruct later.
- *Rate limit it.*  Recovery is low-volume by nature, so a tight limit costs real users
  nothing and makes attempts expensive and visible.

** The cheapest recovery is the one you never run

If the user still has one working passkey, this is not recovery at all:

#+begin_src ts
await auth.registerPasskey('Backup security key');
#+end_src

Prompt for a second passkey during initial enrollment --- a hardware key in a drawer, or a
second device --- and most of the above stays unused.

* Self-serve signup

Nothing requires a human in the loop.  An automated signup that first proves something about
the person can issue the grant itself; the constraint is that email or SMS must not remain a
standing route into the account afterwards, or the mailbox is back in front of the passkey.

The package ships the state helpers, not the policy:

#+begin_src ts
import {
  describeSignupPhase,
  nextSignupStep,
  SELF_SERVE_SIGNUP_STEPS,
  signupPhase,
} from '@localwebauthn/server';

const phase = signupPhase({
  hasActiveCredential,
  hasPendingEnrollmentGrant,
  hasEnrollmentSession,
});
// 'created' | 'enrollment_issued' | 'enrollment_exchanged' | 'enrolled'
const step = nextSignupStep(phase); // { action, reason }
#+end_src

=SELF_SERVE_SIGNUP_STEPS= is the checklist in order, including the two easy ones to get
wrong: verify two independent channels *before* creating durable access, and deliver to a
bound address rather than one supplied in the request.

The worked implementation --- capability-free proof links, claim-on-reopen so the person
finishes on whichever device they prefer, and for accounts that already have passkeys a
waiting period with "this wasn't me" vetoes from any channel plus cancellation on any
successful passkey sign-in --- is
[[./examples/channels/src/signup.ts][examples/channels/src/signup.ts]].  The demo exercises
all of it with simulated delivery; the channels examples supply real senders.

* Credential kinds
:PROPERTIES:
:CUSTOM_ID: credential-kinds
:END:

A credential carries a host-defined =kind=.  Undeclared kinds --- including =null=, which
every credential created before this feature has --- behave exactly as they did before, so
adding the option changes nothing until you opt in.

#+begin_src ts
credentialKinds: {
  service: {
    interactive: false,             // may not sign in where no kind is named
    canRegister: false,             // may not enroll another credential
    sessionAbsoluteMs: 15 * 60_000, // shorter total session lifetime
  },
}
#+end_src

The reason =kind= exists is that *only server-chosen facts are controls*.  A software client
holds its own private key, so it can assert any =origin=, set the user-verified and backup
flags, and report any signature counter.  =kind=, the challenge, revocation state and heritage
are server rows; everything else in an assertion is a claim the signer makes about itself.

Two limits to internalise:

- =canRegister: false= closes the *session* registration path.  It cannot close the *grant*
  path, which is authorized purely by possession of a single-use token with no session to
  inspect.  Confinement there comes from the grant's own kind
  (=issueEnrollment(userId, { credentialKind: 'service' })=) plus your middleware refusing
  non-interactive kinds --- =auth.interactiveKind(kind)=.
- Kind filters on the bulk revokes let you sign a person out of their devices without
  stopping their nightly export.  The scoped =revokeUserAuthentication= also revokes pending
  grants *of those kinds*, because a live grant of a revoked kind is standing authorization to
  re-enroll straight back in.

* Machine credentials and DPoP

The full design is [[./docs/API-AUTH.org][docs/API-AUTH.org]]; [[./README.org][README.org]]
"A Passkey for a script" is the working code.  What belongs here is the operational surface.

*The client package has two entry points, and the split is the interesting part.*
=@localwebauthn/client= works entirely through the =MachineKeyStore= interface: it asks
a signer for a public key and for signatures, and never handles private key bytes ---
so the same code runs over a file, an agent, a TPM, a Secure Enclave or a cloud KMS.
Generating or reading a *raw* private key, and the credential-file format that carries
one, live in =@localwebauthn/client/file-key=:

#+begin_src ts
import { MachineClient } from '@localwebauthn/client';          // opaque signers
import { importKeyStore, parseCredentialFile } from '@localwebauthn/client/file-key';
#+end_src

Nothing behind that second import is discouraged --- a file-based credential is how a
CLI holds a key.  It is separate so the import line says what the code does, and so a
deployment that uses a platform keystore never reaches it at all.  A test asserts the
default entry point exposes no raw-key operation, and lint forbids the server and
browser packages from importing it.

*A machine route should call =authenticateMachineRequest=, not assemble the check by hand.*
It takes the raw token, derives the session from it, requires a DPoP proof, and refreshes the
session's activity only after the proof holds --- one fail-closed operation:

#+begin_src ts
const { user, session, nonce } = await auth.authenticateMachineRequest({
  sessionToken, proof: request.header('DPoP'), method, url, requireNonce: true,
});
#+end_src

That ordering matters.  Resolving the session first with the default activity touch, then
verifying the proof, would let a thief holding only the bearer token keep the session alive to
absolute expiry without ever signing a proof.  =authenticateMachineRequest= closes that: a
request that cannot prove possession changes no server state, and because the session comes
from the token there is no way to pair a token with a different resolved session.

=verifyDpop= is the lower-level primitive it is built on; verify a proof against an
already-resolved session only if you cannot use the higher-level method.  Either way there is
no per-session key material: the expected thumbprint is *derived* from =credentials.public_key=,
so the per-request check reduces to "signed by the same key that opened this session".  The
only new state is a =jti= replay cache.

Server-issued nonces are opt-in, because they cost the client something real --- it must
retain the latest =DPoP-Nonce= and retry once when challenged:

#+begin_src ts
dpopNonce: { rotationMs: 60_000 }
#+end_src

They are stored in the database, keyed by time slot, so every server in a deployment
converges on one value per slot without a shared secret --- whichever inserts first decides,
the rest read it back.  A nonce is *not* a secret; the server hands the current one to any
caller.  Its only property is being unguessable *in advance*, which is what stops a key holder
pre-generating proofs.  Both the current and previous slot are accepted so a rotation landing
mid-flight does not reject a proof built moments earlier.

=dpopChallenge(nonce)= returns the =WWW-Authenticate= / =DPoP-Nonce= header pair for the
=dpop_nonce_required= case, so hosts stop hand-rolling four steps.

A custom store needs the three DPoP methods only if you use this feature: they live in a
separate =LocalWebAuthnDpopStore= contract, and the service checks for them where it uses
them, throwing =invalid_configuration= naming the missing ones.  Every official adapter
implements both.

* Rotating an API credential

Rotation is not incident response --- it is maintenance, and it should be dull enough
to do on a schedule or on a hunch.  There is no re-keying step and no downtime,
because a user may hold several credentials of the same kind at once:

1. *Mint the replacement.*  The old credential keeps working.
2. *Deploy it* --- write the new =.env=, restart the script, confirm it works.
3. *Revoke the old one.*  =revokeCredential(userId, oldId, { allowLastCredential: true })=.

Both credentials are live between steps 1 and 3, so nothing is ever down and the
window is as long as you want it to be.  =examples/demo/tests/machine.test.ts= runs
exactly this sequence and asserts the overlap.

#+begin_src ts
// Step 3, after the new credential is deployed and verified.
await auth.revokeCredential(userId, retiringCredentialId, { allowLastCredential: true });
#+end_src

=allowLastCredential= is needed because the last-credential guard is scoped by kind:
it exists to stop a person locking themselves out of their *own* account, and an API
credential is never a person's way back in.  Rotation is also why
[[./SECURITY.md][SECURITY.md]] treats key custody as a cost to be *bounded* rather
than a problem to be solved perfectly --- a credential you will happily replace is
worth far less to whoever finds a copy of it.

Rotate when:

- a laptop, phone or CI runner that held the file is lost, sold or decommissioned;
- somebody with access to it leaves;
- the file may have gone somewhere you did not intend (a clipboard manager, a chat, a
  screenshot, a repository);
- on a schedule, so the procedure is proven before you need it in a hurry.

If the old credential enrolled anything --- it cannot, when
=canRegister: false= --- =credentialDescendants= shows what, and
=revokeCredentialTree= retires the subtree instead.

* Provisioning pages: showing a secret once

If a page in your application displays credential material --- a minted API
credential's private key, or any show-once token --- it needs hardening, and this is
the same hardening every service with a "copy your API key now" page needs.  It is
well-trodden, not exotic: about six headers, plus one rule about what else the page is
allowed to load.

#+begin_src ts
import { provisioningPageHeaders } from '@localwebauthn/server';

// On the response that carries the document (and its assets):
for (const [header, value] of Object.entries(provisioningPageHeaders())) {
  response.headers.set(header, value);
}
#+end_src

It sets a CSP with no =unsafe-inline= (the one that matters --- one injected or
third-party script can read the key out of the DOM), =frame-ancestors 'none'=,
=Cache-Control: no-store=, =Referrer-Policy: no-referrer=, a permissions policy that
asks for nothing, and cross-origin isolation.  Pass =scriptNonce= if the page cannot
be built from external scripts alone, and =connectSrc= for extra API origins.

*Headers are necessary, not sufficient.*  The things they cannot reach:

- *Third-party JavaScript.* Analytics, tag managers, session replay, a chat widget:
  any of them can read the DOM.  Serve a provisioning page from a *minimal, dedicated
  origin* with only your own bundle, so its blast radius is not your whole app's.
- *Service workers*, which can intercept and cache responses.  Register none there.
- *Copies that outlive the page.*  Clipboard history, the Downloads folder, backups of
  either, terminal scrollback, an SSR payload, an error reporter or a session-replay
  tool that serialises application state.  Keep the value out of anything that
  persists or transmits state, and say so in the UI --- the demo does.
- *Erasure.*  Clearing a buffer is hygiene, not a guarantee: WebCrypto does not
  promise that key material is destroyed when a reference is dropped.  Never tell a
  user a value is "gone".

Two design choices reduce the risk more than any header:

1. *Make the credential cheap to replace.*  Revocation is one call, heritage records
   what each credential created, and minting another costs seconds.  A secret you can
   discard on suspicion is worth far less to an attacker than one you cannot.
2. *Do not put the key in a browser at all.*  Generate a script's key **on the machine
   that will run the script**, so the only copy is born where it lives and no
   clipboard, download or page is ever involved.  Browser minting is a
   *compatibility* path; see [[./docs/API-AUTH.org][docs/API-AUTH.org]].

* Credential heritage

Every credential this package creates was authorized either by an enrollment grant or by an
existing credential's session.  Four columns record which:

| Column               | Meaning                                                 |
|----------------------+---------------------------------------------------------|
| =createdVia=         | ='enrollment'=, ='session'=, or =null= for pre-2.x rows |
| =parentCredentialId= | the credential whose session authorized this one        |
| =grantId=            | the enrollment grant it was redeemed from               |
| =approvedByUserId=   | who approved that grant                                 |

#+begin_src ts
await auth.credentialLineage(userId, credentialId);    // root first, back to the enrollment
await auth.credentialDescendants(userId, credentialId); // index 0 is the credential itself
#+end_src

=grantId= and =approvedByUserId= are deliberately *not* foreign keys: grants are reaped by
=cleanup=, so these are copied facts about the past.  =parentCredentialId= may be a real
foreign key only because credentials are never deleted.

* Audit events

=onEvent= receives every lifecycle event.  It is best-effort --- persist what matters rather
than treating the callback as the record:

#+begin_src ts
onEvent: (event) => void auditLog.write(event),
#+end_src

| Event                         | Emitted when                                      |
|-------------------------------+---------------------------------------------------|
| =enrollment.issued=           | a grant is created                                |
| =enrollment.exchanged=        | a token is redeemed for an enrollment session     |
| =enrollment.completed=        | a passkey is registered against that grant        |
| =enrollment.revoked=          | a pending grant is superseded or revoked          |
| =credential.registered=       | a passkey is created                              |
| =credential.authenticated=    | an assertion verifies                             |
| =credential.revoked=          | a credential is revoked                           |
| =session.created=             | a session begins                                  |
| =session.revoked=             | a session ends                                    |
| =user.sessions_revoked=       | bulk session revoke, with =count= and any =kinds= |
| =user.authentication_revoked= | bulk credential revoke, with any =kinds=          |

Return values are the durable record where one exists: =issueEnrollment= returns
=supersededGrantIds= precisely so a host can write the replacement down without depending on
the event.

* Errors

Every failure is a =LocalWebAuthnError= with a =code= and an HTTP =status=.  Map them once:

| Code                         |      Status | Means                                                  |
|------------------------------+-------------+--------------------------------------------------------|
| =invalid_configuration=      |         500 | the host asked for something inconsistent              |
| =invalid_enrollment=         | 400/403/404 | bad, expired, consumed or revoked link; unknown user   |
| =enrollment_not_authorized=  |         403 | no valid grant or session authorizes this registration |
| =invalid_ceremony=           |         400 | challenge missing, expired or already used             |
| =registration_failed=        |         400 | the attestation did not verify                         |
| =authentication_failed=      |         401 | the assertion did not verify                           |
| =registration_not_permitted= |         403 | this kind is =canRegister: false=                      |
| =credential_not_found=       |         404 | no such credential for this user                       |
| =last_credential=            |         409 | would remove the person's only credential of that kind |
| =invalid_dpop_proof=         |         401 | absent, malformed, replayed, or wrong key              |
| =dpop_nonce_required=        |         401 | answer with =dpopChallenge()= and let the client retry |

Do not surface the =reason= detail attached to DPoP messages: it distinguishes "wrong key"
from "replayed".

* Migrations and versioning

The service API, store contract and database schema follow SemVer; breaking changes arrive
only in a new major version with notes in [[./docs/MIGRATING.md][docs/MIGRATING.md]].

Schema upgrades are versioned and applied in place: =migrateSqlite=, =migratePostgres= and
=migrateD1= read the stored version and run only what is missing.  A database at version 1
--- the only version ever published --- upgrades on the next start.

Two traps if you extend the schema yourself: =LOCALWEBAUTHN_SCHEMA_SQL= must contain no
=--= comments (the statement splitter collapses whitespace and would comment out the
following statement), and a new *table* needs only its name in that version's =newTables=,
because the upgrade path lifts its =CREATE TABLE IF NOT EXISTS= and indexes from the full
schema in the right dialect.

* Reading the code

Every SQL statement the package executes is collected in
[[./packages/server/src/queries.ts][packages/server/src/queries.ts]], so a reviewer can read
the data layer in one file.  [[./SECURITY.md][SECURITY.md]] gives the per-table inventory of
what is stored and what each value is worth to whoever reads it, what a disclosure does and
does not cost, the security boundary, the host's duties, and how to report a vulnerability.

If you are auditing and do not issue API credentials, =packages/server/src/dpop.ts= and the
=credentialKinds= handling are the parts you can skip.
